# 前端业务逻辑重构:平台 / 服务(SUT) / 场景 / 运行 四域 + 工作台壳层

## 域划分定案

**四个业务域 + 一个公共资产域**(逻辑组织轴):

| 域(目录名) | 业务对象 | 收纳的现有逻辑 |
|---|---|---|
| **平台 `platform`** | 平台管理与认证入口 | 用户管理业务规则;Login/Register 视图归属 |
| **服务 `sut`** | 被测服务/SUT | 服务凭据(Auths/AuthSelectorModal 业务)、carry 值表(carry-drift/entries/hint/csv 规则)、**适配中心**(接口变更检测,adaptation-merge;admin/member 双视图为域内呈现分发) |
| **场景 `scenario`** | 场景定义 | 场景库/composer 的业务规则(declarations 状态解析/清洗/树/绑定/搜索、draft-lint、var-registry、tpl-refs、query-context、assertion-registry)、数据集规则(dataset-grid/csv-dataset 的业务校验)、**方案定义**(SchemeWorkbench 的方案构建) |
| **运行 `run`** | 执行与发起 | **方案→可执行的转换**(convertDraftToExecutable/schemeToOverlay)、**serviceRows/authOptions 推导**(现三处重复)、RunRequest 构建、执行状态(executionStatus)、轮询预算规则、removeExecution |
| **资产 `assets`** | 工作台级公共资产 | 常量池业务(pool-var、常量与 generator 目录的消费规则) |

**基础设施(非业务域,横切)**:认证态/token 刷新/HTTP 401 管道、plate 客户端、共享 UI(TopNav/TagInput 等)、通用 utils(json/links/filters 等)。四域都只准单向依赖它。

**域间依赖方向(单向,防重新缠绕)**:
- 场景 → 运行(场景页发起运行、嵌运行面板)、场景 → 资产(编排引常量)、场景 → 服务(编排选凭据)
- 运行、平台、资产 **不反向**依赖场景(运行按 id 自拉数据)
- 全部 → 基础设施;`import/no-cycle` 全局禁环

**工作台(产品壳层,非逻辑域)**:落地为路由分区 + 角色分发 —— 普通用户工作台(场景/运行/资产/服务凭据/适配 mine 视图),管理员区(用户管理/适配全量/carry 配置)。现有 `meta.requiresAdmin` + `scope=mine` 已是雏形,本次只做导航分区归档,不新建逻辑。

## 域内逻辑分层(解决"平铺"的核心)

每域内部单向四层:`api(数据访问)→ domain(纯业务规则,零 Vue/Pinia 依赖,可纯函数单测)→ store(状态)→ views/components(UI)`。本次重点是把现在长在**视图/store 里的业务规则**抽到各域 `domain/`。

## 实施步骤(先逻辑后目录;每步 vue-tsc + vitest 全绿再提交)

1. **骨架与规则**:建 `src/domains/{platform,sut,scenario,run,assets}/domain/`;加 tsconfig/vite/vitest 别名 `@domains/*`;ESLint 精简接入 + 两条边界规则:domain 层禁止 import vue 组件/pinia/`@/views|@/components`,`import/no-cycle` 禁环
2. **场景域抽离**(最大):`utils/declarations.ts`(927 行 30 导出)按职责拆到 `domains/scenario/domain/`(state-resolve/sanitize/tree/bindings/search/value-sources 子模块),draft-lint、var-registry、tpl-refs、query-context、assertion-registry 规则、`types/assertion-registry.ts` 里的运行时函数 `isLegacyEntry()` 同步归位;原 `utils/declarations.ts` 改为薄 re-export,10 个消费方零改动,测试路径不动
3. **运行域抽离**:`convertDraftToExecutable`/`schemeToOverlay` 迁出 `stores/scenario-draft.ts` → `domains/run/domain`;**serviceRows/authOptions 三处合一**(CaseComposer.vue:495、RunPanelHost.vue:75、SchemeWorkbench.vue:145 → `domains/run/domain/service-rows.ts`);executionStatus/removeExecution 规则归位
4. **服务域抽离**:carry-csv/drift/entries/hint、adaptation-merge 的规则函数 → `domains/sut/domain/`;数据集业务校验(dataset-grid/csv-dataset 中非解析的规则)归场景域
5. **资产域抽离**:pool-var 及常量消费规则 → `domains/assets/domain/`
6. **收尾**:路由/TopNav 按"工作台 vs 管理员区"分区注释归档;`docs/frontend-architecture.md` 记录四域+工作台模型、依赖方向、域内分层约定(第二阶段目录迁移的设计依据)

**抽离手法**:业务规则以纯函数形式搬入 domain,视图/store 原处保留薄委托(调用 domain 函数),行为不变;94 个测试文件全程作安全网,`utils/declarations.ts` 等用 re-export 保持消费方稳定。

## 非目标(第二阶段再做)

## 风险与兜底

- 只搬逻辑不改行为,`serviceRows` 三处合一靠现有 composer 测试(24 个)守护
- re-export 保底让消费方改动最小化,任何一步可独立回滚
- domain 层"零 Vue 依赖"由 ESLint 规则长期锁住,防再次平铺
