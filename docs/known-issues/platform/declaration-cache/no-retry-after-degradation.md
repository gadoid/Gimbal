# 降级失败后没有重试通道（会话内停留从严姿态）

> **模块**：`gimbal-platform/frontend`（`useEndpointFull` 失败负缓存 × `useInjectableSurface` 的退避重试与失败态呈现）
> **状态**：**已修复**（阶段二 Task 8：有界退避重试 + 失败态可见）
> **来源**：架构收敛执行会话自查（非 spec 条目）
>
> 以下正文是**修复前**的记载（保留历史，不改写）。被本波修复作废的陈述，
> 逐条更正见文末 [修复记录](#修复记录)。

---

## 0. 机制

契约取数失败会写一个**有窗口的负缓存**，窗口内不再发起：

```ts
// src/gimbal-platform/frontend/src/composables/useEndpointFull.ts:46
export const FAILED_RETRY_MS = 10_000
// :64-67  窗口内直接返回 undefined
// :77-80  catch 里 failedAt.set(endpointId, Date.now())
```

而状态是**持久**的（只有成功才清）：

```ts
// :74  成功：failedAt.delete(endpointId)
// :92-96  endpointFullState：已缓存 → ''；failedAt 命中 → 'failed'；否则 'loading'
```

判定面把 `'failed'` 读作**已落定的答案**（不是「在途」），于是姿态**从严**：

```ts
// src/gimbal-platform/frontend/src/composables/useInjectableSurface.ts:103-104
const pending = computed(() =>
  neededEndpoints.value.some((eid) => endpointFullState(eid) === 'loading'))
// :159（同文件）suspended = pending && 全部 issue 都是 path-unresolvable
```

即：取数失败 ⇒ `pending === false` ⇒ `path-unresolvable` 归 `intrinsic`（**真死**）⇒ 进入 `deadIds`（`:169-172`）。

**而重试只有一个触发口**：`ensure()`（唯一的取数副作用），它由两处调用：

```ts
// :83
watch(stepEndpointIds, () => ensure(), { immediate: false })
```

以及各宿主的挂载钩子 —— `components/composer/RunPanelHost.vue:102`、`views/AssertionRegistryEditor.vue:225`、`views/CaseComposer.vue:522`、`views/CaseDataSetsList.vue:140`。

**没有任何定时器、可见性回调、或读路径触发的重试** —— 后者是**故意**的：读/取分离（裁定 C18）就是为了让渲染期零请求（IS-7），所以读函数不许内部取数。

---

## 1. 后果

**触发条件**：用户进入页面（挂载）时 plate 抖动一下（超时 / 5xx / 信封坏）⇒ 该端点的负缓存被写下。

**影响**：这一次会话里，判定面**一直**按「声明面不可得」的姿态工作 —— 锚在契约声明上的条目被算作 `intrinsic` 死条目：

- 运行面板里**不可勾选**（`deadIds` 是禁选的唯一派生，`:43-47`、`:169-172`）；
- 数据页 / 断言管理里标成「悬空」。

**恢复路径**（只有两条，且都不是自动的）：

1. **步骤面变化**：`stepEndpointIds` 变化（增删步骤 / 改某步的 `endpoint_id`）⇒ `watch` 触发 `ensure()`；
2. **重新挂载**：路由切走再回来 / 刷新页面 ⇒ 宿主 `onMounted` 触发 `ensure()`。

**注意一条不成立的直觉**：**修改条目不会重试**。`neededEndpoints`（条目引用面）只影响 `pending` 的计算，不触发 `ensure()`（`ensure` 的输入是 `stepEndpointIds`）—— 用户改了条目、甚至新增了条目，取数**不会**重来。请勿按「改一下条目就好了」去指导用户。

**另有一条时间边界**：负缓存窗口是 10s，且**只在 `ensureEndpointFull` 内部判定**。所以即使窗口已过，没有新的 `ensure()` 也**不会**重发；反之在窗口内即使调 `ensure()` 也**不会**重发。

---

## 2. 优先级：P1

按 README：**触发条件明确、可控、规避成本低**。

- 触发条件明确：**挂载时刻**的 plate 抖动（一次失败即锁一整个会话）；
- 可控 + 规避成本低：刷新页面 / 切走回来即可恢复，且失败是「从严」而非「从宽」—— 不会错误执行，只会少给候选、多标悬空；
- 不是 P0：不产生非预期的业务结果（不会静默注入错值），最坏是用户**看到假悬空**、无法选择本可选中的条目；
- 若把「条目被误标悬空导致漏跑注入」视为业务结果（用户以为跑了、其实条目被 skip 且他只当成 UI 灰显），**应改判 P0** —— 该衔接见 `judge-degraded-observability.md` 的 `entriesSkippedWhileDegraded`（那条遥测正是为这种「降级造成跳过」准备的）。

---

## 3. 读者应当怎么做

1. 遇到「刚打开页面时条目一片悬空、刷新后好了」⇒ 按本条判据解释：挂载时刻 plate 抖动 + 无重试通道；
2. 需要恢复：**刷新页面**或**切走再回来**（不要等，也不会自己好）；
3. 若要收口（**方向备查，不是结论**）：给 `ensure()` 加一次「失败后延时重试」或把 `endpointFullState` 的 `'failed'` 在窗口到期后回落为 `'loading'`（使 `pending` 重新为真、并触发一次取数）—— 两条都要小心 **IS-7**（渲染期零请求）与负缓存防抖的既有约定，不要在读路径里发请求。

---

## 4. 何时重开

1. **plate 抖动期的用户反馈**集中在「条目灰显 / 不可勾选」；
2. **H 落点裁定**（spec §7）：若判定面改为后端算、前端消费，本条的触发时机模型整体改变；
3. **`ensure()` 触发时机调整**（新增定时器 / 可见性触发 / 步骤面之外的依赖）—— 上界与恢复路径都要重核；
4. **IS-7（渲染期零请求）约定被修订** —— 那会给「读路径重试」打开口子。

### 1. 现在是什么

- **降级信号**：`useInjectableSurface` 新增 `degraded`（裁定 R21 的**宽**定义）——
  `neededEndpoints`（被条目引用的端点）里至少一个 `endpointFullState(eid) === 'failed'`。
  该函数在「续用旧面 + 本次刷新失败」那一格同样返回 `'failed'` ⇒ **续用旧面也算降级**
  （没有收窄成「没有可用面」，也没有给 `endpointFullState` 加第三个返回值）。
- **有界退避重试**：降级后按 `RETRY_BACKOFF_MS = [10s, 30s, 60s]` 三档**各试一次**，
  **试满即停**（`RETRY_BACKOFF_MS[tier] === undefined` ⇒ 不再排期）。链是**串行**的：
  下一档在上一档取数**落定之后**才排；成功 ⇒ `degraded` 转 false ⇒ 链自己收尾，
  不退化成常驻轮询。`degraded` 每次变化都把 `retryTier` 归零（新的降级从头再来）。
- **每一档都走 `force`**：`ensureEndpointFull(eid, { force: true })` 跳过 TTL 与失败负缓存
  两道闸（复核整改 ②；已在飞则复用那个 Promise，不重复发）。⇒ 正文 §1 末尾那条
  「在窗口内即使调 `ensure()` 也不会重发」现在**只对不带 `force` 的自发取数**成立。
- **覆盖面 = 全部步骤端点**（与 `ensure()` 同面）：`retryOnce` 遍历 `stepEndpointIds`，
  不只被条目引用那几个 —— 只被画布需要、无条目引用的端点失败也一并恢复（用例 IS-16）。
  **触发面**仍是 `degraded`（= 被条目引用的端点，与 `pending` 同面）。
- **失败态可见 + 三个手动入口**（复核整改 ①）：编辑器（`AssertionRegistryEditor`）、
  画布（`CaseComposerCanvas`）、运行对话框（`RunDialog`；两个宿主 `RunPanelHost` 与
  `views/CaseComposer.vue` 各接一侧）共用组件 `components/composer/SurfaceNotice.vue`
  呈现降级 / 换面，并带**手动重试**入口（`surface.ensure({ force: true })` /
  `ensureEndpointFull(eid, { force: true })`）。**「条目不可勾选」的症状现场（运行对话框
  的注入条目复选框）现在有提示与重试入口** —— 那正是本条最刺眼的一格。
- **链随宿主作用域销毁而停**：`onScopeDispose` 既清**待定**的定时器，也置 `disposed`
  让**在飞**那一档落定后不重挂（两半各管一条路径，复核整改二轮）。
- **读路径仍不发请求**：退避定时器落在组合式内（属于「取」，与挂载时的 `ensure()` 同类）；
  IS-7（渲染期零请求）与画布的 CANVAS-FETCH-1 / 2 **原样绿**，本波未修订该约定。

### 2. 更正正文里被作废的陈述

1. **「而重试只有一个触发口」不成立**：现在是挂载、步骤面变化、降级退避（自动）、
   以及三个宿主的**手动重试入口**（显式动作）。
2. **「恢复路径只有两条，且都不是自动的」不成立**：自动路径见 §1；「刷新页面 / 切走再
   回来」仍然有效，但不再是唯一出路。
3. **「修改条目不会重试」仍成立，结论要改说**：`ensure()` 的输入面仍是步骤端点
   （`stepEndpointIds`），改条目**不触发**取数；但降级之后现在有自动退避与可见的重试
   按钮兜住，不再「只能等刷新」。
4. **§1「另有一条时间边界」收窄**：负缓存窗（`FAILED_RETRY_MS = 10s`）只拦**不带 force
   的自发取数**；退避的每一档与三个手动入口都走 `force`，窗口吞不掉任何一档。
5. **§0 的代码行号已失效**（本波改了同文件多处）：以符号名为准
   （`FAILED_RETRY_MS` / `ensureEndpointFull` / `endpointFullState` / `ensure`）。
6. **§2 的优先级论证**（触发条件明确、方向从严、不产生静默错值）**保留原判**。

### 3. 诚实的残余（本波**未**消解）

1. **退避表试满后需手动点**：`[10s, 30s, 60s]` 三档走完（约 100 s）仍未成功 ⇒ 之后
   **不再有任何自动尝试**，恢复靠人工点一次重试（编辑器 / 画布 / 运行对话框任一处）。
   即**不是完全自愈**：自动通道**有界**，兜底是人的一次点击。
2. **挂载进「已降级」共享缓存的宿主，一次自动尝试都没有**：`watch(degraded)` 不是
   `immediate` ⇒ 若挂载那一刻 `degraded` 已经为真（共享缓存是模块级的，前一个宿主留下的
   失败态还在），新宿主**不会**排任何退避链，只剩手动入口。该性质已由 T8 的 IS-15
   第二段**实测复现**（用例里显式 `_resetEndpointFullCacheForTest()` 并注明原因）。
3. **只被画布需要、无条目引用的端点**：它失败时**不**点亮降级信号（触发面是「被条目
   引用的端点」）⇒ 没有自动退避；由画布的手动重试入口兜住（两侧读同一份缓存，手动
   那一次同时恢复两侧）。这是按裁定保留的一格（裁定 R21 / R29 / R30），不是遗漏。
4. **手动点击受「已在飞则复用」约束**：恰有一次取数在飞时点击不额外发请求（复用其
   结果，语义正确，EF-10 钉住）；这不再是空操作 —— 窗口内的点击真发（EF-9）。
