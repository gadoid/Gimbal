# 配置页与场景预设池：问题与改造建议

> 日期：2026-11-24
> 性质：配置模型与产品语义收口
> 状态：仅调研，未实施

## 1. 结论

配置页目前不能直接删除，但应该拆成两个清晰概念：

1. **执行配置**：解决“这次执行使用哪些身份绑定和运行覆盖”；
2. **场景预设池**：解决“新建或编辑场景时，复用一套服务、实例、身份和凭证引用关系”。

两者可以共享部分数据结构，但不应继续共用一个模糊入口，也不能把预设装填等同于运行时配置选择。

## 2. 当前实现

### 2.1 执行配置

执行配置保存：

- 服务引用；
- 服务别名到身份槽位的绑定；
- 存量 carry 覆盖；
- 用户范围或项目范围；
- 默认配置标记。

它不保存服务地址，也不保存凭证明文。证据：[`ExecConfigsView.vue:729`](../../src/gimbal-platform/frontend/src/views/ExecConfigsView.vue#L729)、[`ExecConfigsView.vue:1428`](../../src/gimbal-platform/frontend/src/views/ExecConfigsView.vue#L1428)。

运行时语义也不是简单的“加载一个配置”：

- 只有显式选择的配置贡献身份绑定；
- 默认配置与显式配置的作用不同；
- 私有区和项目区对 carry 的消费规则不同。

证据：[`exec_config.py:97`](../../src/gimbal-platform/backend/app/services/exec_config.py#L97)。

### 2.2 项目执行配置

后端已经支持项目 scope 的列表、创建、编辑、默认、复制、删除和漂移，见 [`exec_configs.py:204`](../../src/gimbal-platform/backend/app/routers/exec_configs.py#L204)。

但项目配置页已经主动撤下项目执行配置变体，只保留默认环境、实例与凭证匹配、身份装载、项目凭证、生效预览和 carry 同步，见 [`ProjectConfigPanel.vue:1`](../../src/gimbal-platform/frontend/src/components/project/ProjectConfigPanel.vue#L1)、[`ProjectConfigPanel.vue:203`](../../src/gimbal-platform/frontend/src/components/project/ProjectConfigPanel.vue#L203)。

因此项目执行配置目前是“后端存在、前端不可维护”。

### 2.3 场景直接装配

场景编排已经直接选择服务实例和调用身份，并通过 `service_scope` 保存 `{service, envId}` 引用，见 [`CaseComposerConfig.vue:1083`](../../src/gimbal-platform/frontend/src/components/composer/CaseComposerConfig.vue#L1083)。

`service_scope` 只是预选和凭证映射域，不是执行环境承诺；执行环境仍由步骤引用的身份标签决定，见 [`service_scope.py:11`](../../src/gimbal-platform/backend/app/services/service_scope.py#L11)。

## 3. 当前问题

### 3.1 “配置”同时指多种东西

当前语境至少包含：

- 个人执行配置；
- 项目执行配置；
- 项目默认环境；
- 项目层 carry 默认值；
- 场景内的服务范围与身份绑定。

用户无法稳定判断某个“配置”究竟影响编辑、执行还是项目默认行为。

### 3.2 个人与项目能力不对等

个人执行配置有完整前端，项目执行配置只有后端。若目标是项目完整继承个人能力，这里属于明确缺口。

### 3.3 缺少可复用的场景预设

场景内直接装配灵活，但每次新建或调整都要重复选择。现有执行配置不是为“装填场景草稿”设计的，直接复用会产生语义混淆。

### 3.4 预设装填可能带来隐式副作用

身份条目是共享引用。装填预设如果直接修改全局身份条目，会影响所有引用该身份的场景，见 [`UsersCard.vue`](../../src/gimbal-platform/frontend/src/components/composer/UsersCard.vue)。

因此预设不能通过“顺手改全局身份”来完成装填。

### 3.5 凭证和环境语义容易被误解

预设可以描述引用关系，但不能：

- 保存凭证明文；
- 保存服务地址快照；
- 把某个环境承诺为永久执行环境；
- 把其他用户的个人凭证引用带给当前用户。

## 4. 建议的目标模型

### 4.1 执行配置

保留为运行时配置，建议明确：

- 作用域：个人或项目；
- 使用方式：默认或显式选择；
- 内容：身份绑定、允许的运行覆盖；
- 不含：地址、凭证明文、场景步骤。

项目执行配置是否恢复前端，应作为独立决策，不与预设池捆绑。

### 4.2 场景预设池

预设是作者侧模板，建议保存：

| 字段 | 含义 |
|---|---|
| `id`、`name`、`description` | 预设标识 |
| `scope`、`scopeId` | 个人或项目可见范围 |
| `serviceScope` | 服务与实例引用 |
| `identityBindings` | 服务别名到身份槽位的引用 |
| `credentialRefs` | 可选的账号引用，不含明文 |
| `tags` | 分类与检索 |
| `version` | 后续变更与冲突识别 |

预设不是执行快照。地址始终由 Deployment 解析，凭证始终从个人池或项目池读取。

### 4.3 装填流程

建议流程：

1. 用户在场景中选择“从预设装填”；
2. 系统展示预设包含的服务、实例、身份和凭证引用；
3. 校验当前用户或项目是否有权使用这些引用；
4. 展示与场景现有配置的差异；
5. 用户选择覆盖、合并或仅补空项；
6. 只修改当前场景草稿；
7. 保存时再走现有身份引用和凭证池校验。

不得在装填过程中静默修改全局身份条目。

### 4.4 冲突与缺失处理

- 预设引用的服务已删除：列出缺失项，不静默丢弃；
- 凭证在当前池不可用：标记缺失，不复制他人凭证；
- 场景已有绑定：默认不覆盖，必须由用户确认；
- 身份槽位冲突：展示来源和影响范围；
- 跨项目预设：仅允许引用当前项目可见的资源。

## 5. 配置页改造建议

建议将配置区拆为：

- **执行配置**：保留个人与项目运行时配置能力；
- **场景预设**：新增预设池，提供新建、编辑、复制、预览和装填；
- **项目默认配置**：继续承载项目默认环境、carry 和实例凭证匹配，不再与预设混在一起。

如果产品决定项目只保留一套默认配置，则应同步简化个人执行配置，避免长期维持两套不对等心智。

## 6. 迁移策略

- 不自动把现有执行配置转成场景预设；
- 提供显式“复制为预设”入口，转换前展示差异；
- 新预设只影响后续主动选择，不批量修改存量场景；
- 存量项目执行配置继续可读、可执行，直到产品明确退役；
- 身份和凭证引用在装填时重新校验，不迁移秘密材料。

## 7. 验收标准

- 用户能清楚区分执行配置、项目默认配置和场景预设；
- 预设装填只修改当前场景草稿；
- 装填不写入地址或凭证明文；
- 缺失引用有明确提示，不静默消失；
- 现有绑定不会被默认覆盖；
- 项目预设不能泄露他人个人凭证；
- 默认执行配置与显式执行配置语义不变；
- 项目执行配置是否开放有明确产品结论；
- 存量场景和存量配置不因预设池上线被自动改写。

## 8. 待拍板事项

1. 项目执行配置是否恢复完整前端？
2. 场景预设是个人、项目还是两者都支持？
3. 预设是否允许保存账号引用，还是只保存身份槽位？
4. 装填冲突默认采用“仅补空项”还是“整组覆盖”？
5. 现有执行配置是否提供显式复制为预设的迁移入口？
