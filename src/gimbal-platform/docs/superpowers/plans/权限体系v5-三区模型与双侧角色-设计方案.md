## 0. 一句话模型

**平台三级角色（Super Admin / Admin / User，只管全局）× 项目三级角色（项目管理员 / 项目成员 / 项目用户，只管项目内）× 三区（私有 / 项目 / 公共）× 执行身份跟区走（个人 / 项目 / 平台）× 令牌能力 ⊆ 本人。**

两条公理贯穿全文：

1. **分界线 = 影响半径**：只影响自己 → User 的私有区；影响一个项目 → 项目角色；影响全局/不可逆 → Admin / Super Admin。
2. **跨用户可见性是稀缺品**：平台角色对他人私有区一律不可见；项目区/公共区对 Admin+ 开放的是审计可见，不是编辑权。

## 1. 背景与动机

现状核对（2026-11-06）确认的六类冲突：

| # | 类型 | 典型表现 |
|---|---|---|
| 1 | 口径分裂 | 执行页详情/行级/事件走 `exec-visible`，日志流/工件/调试走 `exec-owner`——member 打开平台执行，页面能开、日志面板 404 |
| 2 | 双实现漂移 | `can_manage`、`can_read_suite`、系统用户特判各有两份实现且已漂移；约 80 处行内角色比较、≥5 种写法 |
| 3 | 定位矛盾 | member 号称技术运营权，但 carry 批量适配 admin-only、平台凭证可见性无明文 |
| 4 | 过宽漏洞 | suite 版本分布接口无读检查（可遍历私有 suite 成员）；公共报告定义创建者自己改不了 |
| 5 | 语义过载 | `public` 同时表示「对人只读展示」和「平台身份可执行的前提」；`private` 在平台任务上含义漂移 |
| 6 | 理念摇摆 | admin 列表只看自己 vs 审计面全看；删除/下架散落条件化 admin 覆盖分支 |

**共同根因：规则没有单点定义的地方，每个新接口重新发明一次判定。**

讨论演化路径（决策记录，含两次有意识的推翻）：

1. 两张表（能力 × 角色 / 对象 × 动词）收敛判定 → 恒定；
2. 「默认权限 + 额外赋权」被采纳为**求值模型**（share/token scope 本就是赋权通道，显式化），能力级赋权（capability grants）**延后**；
3. 公开双语义：从「不拆+告知」→ 改为 **platform_executable 拆分** → 最终被**三区模型**整体取代（拆分不再需要）；
4. admin 口径「全局可读」→ **被推翻**：私有区对任何平台角色不可见；
5. 「公共不传递执行权」（v4 不变量 7）→ **被推翻**：三区下公共区传递执行权，责任归属由「谁跑归谁、用谁的凭证」解决；持续共享运行交给项目身份/平台任务；
6. 三级角色 user/member/admin → member 溶解（其权力被项目层与两级平台角色吸收）→ 为避免单一 admin 权力过高，恢复三级并更名 **Super Admin / Admin / User**（保管与运维分离）。

## 2. 三区

| | 私有区 | 项目区 | 公共区 |
|---|---|---|---|
| 定位 | 个人调试草稿 | 项目资产 | 模板市场 + 通用过程库 |
| 可见 | 仅属主（**任何平台角色不可见**） | 项目成员（Admin+ 审计可见） | 所有登录用户 |
| 执行 | 属主，**个人身份**（个人凭证） | 项目成员/项目用户，**项目身份**（项目凭证池） | 任何人，**个人身份**（自己的凭证） |
| 编排 | 属主 | 项目管理员 + 项目成员 | 仅维护者（发布者）/平台运营 |
| 归属 | 用户个人 | **项目**（不是某个用户） | 公共区自身（维护者字段可空） |
| 用户删除时 | 见下方删除处置规则 | 保留（作者字段匿名化） | 保留（维护者字段清空） |

补充规则：

- **公共区内容可被项目/私有用例引用为链路步骤**（setup/teardown/chain）；通用过程模板存放于此。
- **执行身份跟区走**是缺省，不是强制唯一：公共区以个人身份执行；平台任务以平台身份执行平台（全局）用例——平台身份即「全局项目」，机制同项目身份。
- **发布到公共区**：任何 User 可从私有区发布自己的用例；项目管理员可从项目区发布。低门槛 + 事后治理（Admin+ 可下架）——§12 待确认项 2。
- **删除处置（评审修订）**：现状已有「删除 / 保留 / 转让」三选一（`users.py` delete_user，P2-2），**转让是离职交接的主路径**（resource_transferred 通知、个人别名转共享、集成模板随新属主）。**转让处置保留到 M2 项目区上线之后**；「私有区一并清理」只有在资产可提升到项目区之后才成为默认——M1 期间所有非公共内容都在私有区，直接按清理走会删掉团队资产。

## 3. 平台角色：Super Admin / Admin / User

**命名决定**：放弃 Owner（与对象属主 `owner_id`/「属主」撞名）；采用 Super Admin / Admin / User。术语纪律：对象归属一律「属主」；平台角色 Admin 在 UI 带语境渲染「平台管理员/管理员」；项目角色永远带「项目」前缀。

**语义**：Super Admin ⊇ Admin ⊇ User（能力包含）；**私有区无破窗通道**——任何平台角色（含 Super Admin）都不能查看他人私有区，唯一越权路径是删除用户时的「转让」处置，且转让只改归属、不读取内容（评审修订：与「紧急时可修一切」二选一，取一致性）；**角色授予/升降级权仅 Super Admin**；末位 Super Admin 保护；首个注册用户自动成为 Super Admin。权力集中靠持有者稀缺 + 全量审计控制，不拆互斥碎片。

| | User | Admin（运维） | Super Admin（治理） |
|---|---|---|---|
| 私有区 | 完全自主 | 不可见 | **不可见** |
| 公共区 | 看 + 执行 + 发布自己的 | + 下架治理 | + 下架治理 |
| 项目区 | 按项目角色 | 审计可见 | 审计可见 |
| 个人令牌 | ✓（能力 ⊆ 本人） | ✓ | ✓ |
| 场景导入（入私有区） | ✓ | ✓ | ✓ |
| 服务别名注册表 | 读 | **写** | 写 |
| 平台任务 / 平台令牌 / 平台身份 | ✗ | **管理** | 管理 |
| 平台凭证池 | ✗ | **可用不可看**（平台任务引用） | **全权（保管）** |
| 用户管理 / 角色授予 | ✗ | ✗ | **✓** |
| 公告 | 读 | 发 | 发 |
| 审计日志 | ✗ | 项目/公共/平台运行 | **全量（含 Admin 行为）** |
| 平台任务暂停告警扇出 | — | **值班对象** | 严重事件 |

**审计与投递可见性细则（全量评估 2026-11-06 补）**：

- **审计日志**记录的是特权动作（令牌操作、carry 变更、投递补发、入站记录），不含私有用例内容 → 对 Admin+ 可见（Super Admin 与 Admin 内容相同，M2 起项目动作入审后按区细分）；私有区对象操作不入特权审计（现状即如此，保持）。
- **投递记录（webhook deliveries）**是令牌触发执行的回调产物，payload 即私有执行结果：**个人令牌投递仅属主可见（Super Admin 亦不可越**——「Super Admin 审计可越」与私有区不可见公理冲突，评审指出后二选一取一致**）**；平台令牌投递对 Admin+ 可见。现状「admin 可看任何一条投递」（`webhook_deliveries.py:117`）按此收窄。

**M1 过渡口径（评审吸收 2026-11-06）**：

- **导入的别名侧门**：导入会新建别名、写 carry 绑定（`scenario_import.py` 头注释明确「导入含建别名/写 carry，与别名写权限一致」——member+ 门当初为此而设）。开放导入给 User 的同时收口：**User 导入仅允许映射到已有别名**，`decision=create`（新建别名/写 carry）要求 Admin+，堵住绕过别名注册表写权限与 alias_name 命名空间抢注的侧门。
- **个人别名**（`owner_user_id` 非空）：现状 admin-only 管理（`service_aliases.py:139`，原注释「人事/内容权不落进技术运营角色」）→ M1 归 **Super Admin**（行为不变直移）；M2 随配置分层重定归属。
- **执行记录对 Admin+ 可见**：`Execution` 没有来源区字段，且场景 visibility 可能在执行后改变、M1 期间公共场景也不许非属主执行——**M1 Admin+ 仅可见平台身份执行**（owner 为系统用户），即 `exec-visible` 去掉「admin 看全部」后的剩余部分；「项目/公共来源」等 M2 在执行创建时写 zone 快照后按区放开。
- **环境**：`Environment` 表有 owner_id/visibility 但 visibility 实际未生效（列表/详情对全员返回全部）。M1 按**全局对象**处理（全员读、Admin+ 写、补审计），不让表 B 把未生效的 visibility 套进私有区规则。
- **令牌对 Admin+ 可读**：他人个人令牌的范围会暴露其凭证别名集合——作为审计元数据可接受，表 B 明示此口径。

member 溶解明细（哪些权力去了哪）：

| 原 member 权力 | 新归属 |
|---|---|
| 服务别名注册表维护 | Admin |
| 全局环境 | **消亡** → 项目配置层（环境是项目属性） |
| carry 默认值 / 批量适配 | **项目配置层**（项目配置变更触发项目内适配） |
| 场景导入 | 开放给所有 User，但 M1 仅映射已有别名、新建别名需 Admin+（§3 过渡口径）；M2 起提升校验接管配置完整性 |
| 个人令牌 | 开放给所有 User（v4 的 member 门槛废止） |
| 平台身份（任务/令牌/凭证池） | Admin（管理）/ Super Admin（凭证保管） |
| 平台暂停告警 member+ 扇出 | 改扇出 Admin |

## 4. 项目角色：项目管理员 / 项目成员 / 项目用户

| | 项目管理员 | 项目成员 | 项目用户 |
|---|---|---|---|
| 项目用例读 | ✓ | ✓ | ✓ |
| 执行（项目身份） | ✓ | ✓ | ✓ |
| 编排修改 | ✓ | ✓ | **✗** |
| 成员管理 / 项目配置（环境/凭证池） | ✓ | ✗ | ✗ |
| 发布用例到公共区 | ✓ | ✗ | ✗ |

- **项目用户 = 对外供给的消费者**：通过 Gimbal 对外能力使用项目自动化、读 + 执行、不可改——为外部调用方设的角色。
- 项目级 API 令牌（**未来，不在 v5 首期**）：权限映射项目用户级，作用域限单项目。
- 项目凭证池：项目管理员配置，成员/项目用户**可用不可看**（同平台池模式）。

## 5. 判定模型：平面合取，深度恒为 1

```
allow(主体, 动作, 对象)
  = 能力门(主体.角色, 表A)                    ← 这类事，这个角色能不能做
  ∧ 对象规则(主体, 动作, 对象, 表B)            ← 这个对象（所在区）上，这个动作行不行
  ∧ 资源边界(主体, 对象引用的资源)              ← 目前仅令牌 scope；人无
  ∨ 显式授权(项目成员关系 / 通道降权后的令牌)
```

- 求值顺序：**通道降权 →（令牌能力 ⊆ 属主能力）→ 表 B 默认 → 显式授权**。
- **平台主体占位（评审吸收）**：`__platform__` 种子 role='user'，表 A 若只按 role 查，会把所有平台令牌/平台任务的执行全部拒掉。求值入口（`require_capability` / 表 A 查找）**先判 `is_platform`** → 命中「平台主体」固定行（platform.execute 等能力集），role 不参与平台主体判定。必须有专门用例守住「平台令牌不因角色被拒」。
- **没有层级**：每个新限制是合取里一个条件，不是一层继承。191 个接口塌缩为 ~12 类对象 × 4 个动词（`read / run / write / manage`）。
- 表 A（能力 × 平台角色）内容即 §3 矩阵；表 B 按区改写骨架：

| 对象所在区 | read | run | write | manage |
|---|---|---|---|---|
| 私有区对象 | 属主 | 属主（个人身份） | 属主 | 属主 |
| 项目区对象 | 项目三角色 ∨ Admin+（审计） | 项目三角色（项目身份） | 项目管理员 ∨ 项目成员 | 项目管理员（成员/配置/发布） |
| 公共区对象 | 所有登录用户 | 所有登录用户（个人身份） | 维护者 | Admin+（下架） |
| 执行记录 | 属主 ∨ 本令牌 ∨ Admin+（**M1 仅平台身份来源**，owner.is_system；M2 起执行创建时写 zone 快照，按项目/公共来源放开） | — | — | 取消：按来源区；删除：属主 |
| 令牌 | 本人 ∨ Admin+ | — | — | 属主；平台令牌 Admin+ |
| 平台凭证池 | ✗（Admin 可引用不可看） | — | — | Super Admin |

- 机制件（M1 落地，M2 原样复用只换表内容）：`Principal` 归一（role / is_platform / token_id / user_id 四属性）、`_ownership.py` 单点判定、三个执行解析器合一、表驱动测试、grep 守卫（**routers 与 services 内**禁行内角色比较——services 里有 `access_token.py`、`integration_runner.py` 的直查判定，评审指出只扫 routers 不够）。

## 6. 配置分层与提升流

| 层 | 归属 | 内容 |
|---|---|---|
| 服务别名注册表 | 全局（Admin 维护） | 系统**身份**的唯一事实（系统 + 名字）；**现状别名行自带 base_url / environment_id / credential_alias 绑定、一服务多别名**（`<服务名>-<后缀>`，base_service 索引）——M2 须拆表，见下 |
| 项目配置层 | 每项目一套 | 项目环境（host 映射）、项目凭证池、项目级 carry 默认值 |
| 个人配置层 | 每用户 | 个人认证会话、个人凭证 |

- 场景存**别名引用**而非物理地址——用例内容与配置解析天然解耦，分区配置不需要复制用例。
- **别名拆分（评审修正：M2 最大数据迁移）**：现状「别名 = 身份 + 主机映射 + 环境 + 凭证 + carry 绑定」一体存放。M2「环境降入项目配置层」的真实含义 = **把别名表拆成「全局身份（系统 + 名字）」与「按项目的绑定（base_url / 环境 / 凭证 / carry）」两部分**，并把存量别名与 carry 数据迁移过去——这是 M2 最大的一次数据迁移，排期时单列。
- **提升（私有 → 项目）**：内容不动，绑定随执行身份切到项目解析；提升时校验项目配置完整性（缺环境绑定/缺凭证 → 列缺失项，补齐才准入）。
- 项目配置变更 → 组内用例批量适配：**复用 adaptation 体系**（carry 绑定 + 批量适配），不新发明机制。

## 7. 令牌体系

| 令牌 | 谁可签发 | 能力 |
|---|---|---|
| 个人令牌 | 所有 User | ⊆ 本人：公共区执行 + 自己私有区 + 有执行权的项目用例（按项目角色）；经令牌触发的运行按区定身份与归属 |
| 平台令牌 | Admin | 平台身份（全局项目），只读用例 |
| 项目令牌（未来） | 项目管理员 | 项目用户级，作用域限单项目 |

不变式（v4 保留）：令牌能力恒为属主能力的子集；令牌只见本令牌发起的执行。

## 9. 存量迁移

| 存量 | 迁移 |
|---|---|
| 用户角色 member | → **Admin**（职责几乎无缝：别名维护 + 新增平台任务管理） |
| 用户角色 admin | → **Super Admin**（至少保一个，触发末位保护） |
| 私有场景/suite/数据集 | 原位对应私有区（行为不变） |
| 公共场景 | 原位对应公共区（新增可执行——行为变化，发布公告） |
| share_ref 存量 | M2：逐条转为项目成员邀请或保留只读至过期（细化时定） |
| 全局环境 / carry 默认值 | M2：降入项目配置层；过渡期保留只读（细化时定） |
| 首注册自动 admin | 改为自动 Super Admin（含存量首个真人 admin 核对） |
