# Gimbal 入站授权分级设计 — 个人访问令牌 + 服务/凭证授权白名单(webhook v4)

2026-11-03 · 入站授权分级讨论(jiaoshouxiang × ZCode)

## 结论摘要

**不新增令牌类型、不推翻 v3 身份模型**,在两张现有表(`inbound_credentials` /
`inbound_grants`)之上补三个增量面(前两个 2026-11-03 定稿结构,第三个
同日参数面定稿):

1. **个人访问令牌(PAT)**:个人设置里一键创建,对用户呈现为「一张令牌」,
   底座自动生成一个**个人承载别名**(carrier alias)+ `gic_` + 自签 `ggt_`。
   回调锚、审计两维(调用方系统 × 被代表用户)、吊销/TTL/`last_used` 语义
   全部继承 v3,`inbound_credentials` / `inbound_grants` **零迁移**。
2. **外部调用授权白名单(资源闸)**:服务信息管理里、按别名一张清单——
   **服务白名单**(外部发起的执行允许触达哪些被测系统)与**凭证白名单**
   (允许注入哪些凭证别名)。空清单 = 不限制(兼容现状);配了即白名单,
   dispatch 前校验,违反 `403 resource_not_allowed`。

这两个面各自回应一个真实缺口:**令牌管理入口该在用户个人设置**(v3 的
ggt_ 散落在各别名详情页),以及**外部调用的资源触达面该有显式授权**
(v3 只约束"你是谁、代表谁",不约束"能摸到什么")。

3. **参数化入站(P3,2026-11-03 讨论定稿)**:外部调用可传
   **`vars`(config 声明字段的值)+ `release`(版本钉覆盖,方案级开关)
   + `resource`(Mock/文件,随执行面落地)**;凭证、服务地址、数据集、
   注入**维持 M1 永不开放**——统一原则:调用方能传「数据和选择」,
   不能传「配方」。详见 §5。

改动规模:一张新表 + `service_aliases` 一列(alembic 0033);后端两个
API 族(`me/access-tokens`、`service-aliases/{name}/resource-allows`)+ 
runs 入站分支与 adhoc 校验各插一段闸;前端两个页面区块(个人设置新页
+ InboundPanel 增区块、令牌区块改为跳转)。

## 已定的设计决策

本设计以 2026-11-03 讨论中确认的以下方向为前提(细则见「待拍板事项」):

| # | 决策 |
| --- | --- |
| 1 | 令牌创建入口在**个人设置**,用户自助;不再要求用户挨个进别名页签 grant |
| 2 | 授权勾选在**服务信息管理**,按别名一张清单:服务白名单 + 凭证白名单 |
| 3 | PAT 底座**复用 v3 两件套**(carrier 别名 + gic_ + 自签 ggt_),不新增令牌类型 |
| 4 | 白名单是**资源面约束**,与身份模式正交(个人/平台模式都过闸) |
| 5 | 空清单 = 不限制(兼容存量,收紧是显式动作);本期不做凭证**共享**(只做收紧) |

## 缺口分析

1. **用户视角的令牌管理面缺失**。ggt_ 按「别名×用户」存储,但 UI 只在
   各别名详情页露出——一个在 5 个别名下有 grant 的用户要跑 5 个页面。
   凭证(gic_)同理:我管理的别名的凭证散落在各页。
2. **外部调用的资源触达面无显式授权**。v3 闸门全部回答"你是谁、代表
   谁、配方是否只读",不回答"这次外部触发的执行允许打哪些服务、注入哪些
   凭证"。目前唯一的间接约束是方案(运行方案由属主维护,M1 后入站不能
   自带配方)——但方案是"配方快照",不是"授权清单":换个方案即可换一套
   服务/凭证,没有独立的授权视图与审计。
3. **个人自助摩擦**:个人归属别名(owner_user_id 非空)创建是 admin 专属
   (`routers/service_aliases.py:150-161`),且 external 别名强制 baseService
   指向 plate 目录 integration 服务(`services/service_aliases.py:95-115`)
   ——用户自助建"我的令牌"在今天拼不出来。
4. (本期不做,记录)**共享凭证池**:auth_sessions 严格按 owner 隔离,
   「乙的自动化用甲配的凭证」无通道。白名单本期语义是**收紧**(允许注入
   清单内的),共享(跨 owner 出借)是另一个特性,见「后续方向」。

## 总体架构

```
个人设置「访问令牌」                 服务信息管理「外部调用授权」(按别名)
┌────────────────────┐            ┌───────────────────────────────┐
│ [创建访问令牌]         │            │ 服务白名单: □ fin-service □ …    │
│  名称/有效期/回调地址    │            │ 凭证白名单: □ codfish2     □ …  │
│ 令牌对列表:            │            │ (空 = 不限制;属主/admin 可改)     │
│  gic_+ggt_/到期/最近使用│            └──────────────┬────────────────┘
│  /吊销(整对)          │                           │
└────────┬───────────┘                           │
         │  POST /api/runs(Authorization: Bearer gic_… [X-Gimbal-Grant: ggt_…])
         ▼                                       ▼
   ┌──────────────▶ 认证(deps.principal_or_user,不变)
   │                 ▷ M1 配方禁令(runs.py,不变)
   │                 ▷ 方案物化(_apply_scheme_recipe,不变)
   │                 ▷ ★资源闸(新):服务集 ⊆ 服务白名单 ∧ 注入集 ⊆ 凭证白名单
   │                 ▷ 身份范围(personal: can_run / platform: 公共∨属主+只读,不变)
   │                 ▷ 派发 → 注入解析(resolve_exec_auths ∧ 凭证白名单)
   └────────────────▶ 回调(carrier 别名 / 外部系统别名 base_url + path,不变)
```

PAT 与既有 gic_/ggt_ 的关系:**PAT 不是新的认证路径,是 v3 两件套的
「一键打包」**。自动生成的 carrier 别名与手工登记的外部系统别名走完全
相同的代码路径;对平台而言 `me-<username>` 就是"该用户本人的自动化"这个
外部系统。

## 详细设计

### 1. 个人访问令牌(PAT)

#### 1.1 承载别名(carrier alias)

`service_aliases` 增列 `is_carrier boolean not null default false`
(alembic 0033)。

- **创建**:`POST /api/me/access-tokens` 单事务内建
  `alias_name = "me-" + username`(撞名加短随机后缀)、`kind=external`、
  `owner_user_id=用户`、`is_carrier=true`,随后走既有
  `gic_` 签发与自签 `ggt_` 逻辑。**carrier 别名豁免 baseService 校验**
  (它不对应真实外部系统,目录里没有它的 integration 服务)——校验点在
  `services/service_aliases.py:95-115`,按 `is_carrier` 短路。
- **豁免个人别名 admin-only**:`routers/service_aliases.py:157` 的
  admin 闸对 `is_carrier=true` 放行(member 自助);carrier 别名不走通用
  别名创建端点,只走 `me/access-tokens`,闸天然不经过。
- **可见性**:别名列表(`GET /api/service-aliases`)默认过滤 carrier
  (它是令牌载体,不是服务地址簿条目);admin 视图可显示(排查)。
- **用途边界**:carrier 别名**不得**被场景步骤/方案 serviceBindings 引用
  (它没有 baseUrl 语义;callbackUrl 之外不承诺出站可达)。保存侧校验加
  一条拒绝。

#### 1.2 端点(前缀 `/api/me`,登录即可)

| 端点 | 行为 |
| --- | --- |
| `POST /api/me/access-tokens` | body `{name?, ttlDays?, callbackUrl?}`;建 carrier + `gic_` + 自签 `ggt_`(TTL 同 GRANT 规则);`callbackUrl` 非空则写入别名 `base_url` 并开 `callback_enabled`(密钥自动生成,响应一次性返回);响应 `{tokenPair: {gic, ggt}, alias, expiresAt, callbackSecret?}`——**明文只此一次** |
| `GET /api/me/access-tokens` | 聚合视图:我的令牌对(含 gic_/ggt_ 状态、到期、`lastUsedAt`)∪ 我在**非 carrier** 别名下手工签的历史 grant(兼容存量,标注来源);只回元数据 |
| `DELETE /api/me/access-tokens/{carrier}` | 吊销整对:revoke 该别名下我的 ggt_ + 全部 gic_(别名保留行供审计,对齐"吊销软删"惯例);可选 `?purge=1` 连别名一起删(admin) |

错误码:`access_token_ttl_too_long`(对齐 grant 上限)、
`callback_url_invalid`(必须 http/https 绝对地址)。

#### 1.3 回调

PAT 的回调 = carrier 别名的 `base_url + callback_path`(默认
`/gimbal/callback`,创建时可选覆盖)。投递、签名
(`webhook_outbox.sign_payload`)、退避、`X-Gimbal-Delivery` 去重全部
走既有 outbox,零改动。

#### 1.4 audit 与排查

- `inbound.run` 的 `caller_alias` = carrier 别名名(含用户名,可读);
  detail 增 `via: "pat" | "alias"`。
- InboundActivityPanel(排查面)按别名维度本就可见 carrier 的执行与
  投递——个人设置页的"调用记录"区块直接复用该数据源。

### 2. 外部调用授权白名单(资源闸)

#### 2.1 数据

新表 `alias_resource_allows`(alembic 0033 同批):

```
id           bigserial PK
alias_name   varchar(128) FK service_aliases(alias_name) ON DELETE CASCADE
kind         varchar(16)   -- 'service' | 'auth'
value        varchar(128)  -- 服务名 / 凭证别名
created_by   bigint FK users(id)
created_at   timestamptz default now()
UNIQUE (alias_name, kind, value)
```

语义:**每个 (alias, kind) 维度独立**——配了服务清单则服务受限、凭证
未配则凭证不受限,反之亦然;两个维度都空 = 完全不限制(兼容现状)。

#### 2.2 端点(属主或 admin,与入站设置同权限)

| 端点 | 行为 |
| --- | --- |
| `GET /api/service-aliases/{name}/resource-allows` | 返回 `{services: [], auths: []}` + 候选值域:服务 = plate 目录全量系统名;凭证 = 别名属主凭证池别名 ∪ 该别名经手场景的模板 `${auth.*}` 扫描并集 |
| `PUT /api/service-aliases/{name}/resource-allows` | 整体替换语义 `{services: [], auths: []}`;值不在候选域内仅告警不拒(允许前瞻配置,执行时以实际集校验为准) |

audit:`inbound.resource_allows.write`(detail 记新旧清单)。

#### 2.3 执行闸(runs 入站分支)

插入点:`routers/runs.py` `post_run` 入站分支,方案物化
(`_apply_scheme_recipe`,runs.py:100)之后、身份范围检查之前;
平台/个人模式**都过**(资源约束与身份正交)。

计算与判定:

```python
# 服务集:场景 definition.config.services 的键 ∪ 方案 serviceBindings 的键
# 注入集:场景步骤 ${auth.X.*} 模板扫描 ∪ 方案 injectionEntryIds 物化
#         ∪ 方案 serviceBindings[].authAlias(复用 dispatch 的注入清单计算,
#         单一实现,不另立扫描器)
allow_svc = {r.value for r in allows if r.kind == "service"}
allow_auth = {r.value for r in allows if r.kind == "auth"}
if allow_svc and (svc_set := compute_services(...)) - allow_svc:
    raise 403 resource_not_allowed(kind="service", values=sorted(...))
if allow_auth and (auth_set := compute_injections(...)) - allow_auth:
    raise 403 resource_not_allowed(kind="auth", values=sorted(...))
```

- `compute_services` / `compute_injections` 落在
  `services/inbound_identity.py`(与 `valid_callback_path` 同居,入站
  判定单一出处),dispatch 侧已有注入清单计算则直接复用其函数。
- **adhoc(P3 临时调用)**:`steps[].service` 集过服务白名单,在
  `adhoc_run.prepare_adhoc` 校验族中新增一条(`resource_not_allowed`
  同码);adhoc 无注入语义,凭证维度不适用。
- 错误体:`{code: "resource_not_allowed", kind, values, allowList}`,
  403——与 `not_read_only`/`platform_scope_denied` 同风格,给调用方
  "差哪个"的明确信息。

#### 2.4 集成任务(定时)的失效行为

对齐 grant 失效模式:`integration_runner` 运行前重校验(白名单当前值
vs 任务场景的服务/注入集),违反 → 实例 `paused`,
`paused_reason="resource_not_allowed"`,恢复路径与 grant 一致(清单放行
后 owner/admin 手动启动)。注册时同样预检,不通过直接 422。

#### 2.5 UI

`InboundPanel.vue` 新增第 5 区块「外部调用授权」:

- 两组多选(服务/凭证),候选来自 GET 响应的值域;空态提示
  「未配置 = 不限制」;保存调 PUT。
- 现有「入站凭证(gic_)」「我的 grant(ggt_)」两区块保留
  (admin/属主的系统级管理场景仍在此),但**个人设置页上线后**,普通
  用户的主入口跳转个人设置;区块头部加引导链接。

### 5. 参数化入站:release / vars / resource(P3,2026-11-03 定稿)

现状:入站调用**一个参数都传不进去**——M1 拒一切配方字段,只能原样
重放方案(想换 `bl_no` 只能属主改场景)。定稿的参数面(讨论拍板):
**调用方能传「数据和选择」,不能传「配方」**——地址与凭证恒由服务端
按方案/别名表解析,永不开放。

| 字段 | 语义与物化 | 风险定级 | 开放方式 |
| --- | --- | --- | --- |
| `vars` | 值限定场景 `config.vars` 已声明字段(如 `bl_no`);按 var 的 `kind` 校验值(长度/字符集/枚举),物化进基线隐式覆盖行(direct-fill 通道已存在) | 纯数据,零杠杆 | **默认开放**(声明域内) |
| `release` | 覆盖场景 `meta.plate` 版本钉(完整钉修订,如 `{"fin":"1.0#1"}`);场景链当前不消费 `release`(仅 adhoc 链有),需新接覆盖管道 | **带杠杆**:改被测契约(不同修订=不同端点定义;地址仍锁别名表,不会打到野主机) | **方案级开关,默认关**;开启可限定允许的线(如同线内回退修订) |
| `resource` | `resource.mock`(镜像 image+config+端口映射)/ `resource.file`(文件路径);**引擎与 plate convert 目前均不消费此字段**——已声明、未执行 | 子面分裂:`file` 是数据引用(路径须钉在平台管理工作区,防穿越);`mock.image` 是**镜像引用**,任意镜像=供应链杠杆 | **随其执行面落地一起开放**:`file` 默认开放(工作区路径白名单);`mock` 必须**镜像白名单**(内部 registry / 场景·方案已声明镜像),否则不开 |

要点:

- **优先级**(vars):调用方值 > 生成器默认;仅作用于基线行——方案选了
  数据集多行执行时调用方值不改写行值(避免语义纠缠)。
- **审计**:`vars` / `release` / `resource` 全量进 `inbound.run` detail
  (与 adhoc 的 steps 同款——请求信息可取证);时间线事件 detail 同源。
- **顺序依赖**:resource 的开放以「Mock 部署 / 文件装载执行面」先落地
  为前提(独立工作项,不阻塞 vars/release);resource 白名单(方案稿
  §2)与 release 开关叠加后,外部调用的自由度被完整钉在
  「声明面 × 方案开关 × 资源白名单」三重框内。

## 风险与约束

1. **方案漂移导致外部调用突变 403**:方案维护者改配方引用了新服务,而已
   配白名单未跟 → 下次外部调用 403。缓解:错误体给全信息(差哪个值);
   方案保存页若场景被外部别名经手(audit 可查)且白名单非空,提示维护者
   同步清单;集成任务走 paused(可恢复)而非静默失败。
2. **carrier 别名的目录污染**:靠列表默认过滤 + 不得被引用两条硬约束;
   admin 视图可显性看到,避免"看不见的行"。
3. **空清单=不限制的安全沟通**:这是兼容决策,不是默认安全态——指南与
   UI 文案必须写明"未配置即不限制";需要收紧的管理员要显式配置。
4. **PAT = 密码级凭据**:创建页强提示(等同账号密码,勿入库入仓);
   泄露响应 = 吊销整对(DELETE carrier)一键止损。
5. **白名单值域的漂移**:服务改名/凭证别名改名后清单出现悬空值——执行
   闸按"集合差"判定,悬空值不致误拦,但 GET 视图应标注"已不存在"。
