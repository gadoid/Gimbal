## 0. 背景与三个痛点

1. **admin 的场景库被淹没**。《权限一期》§1.2 给了 admin 全员私有场景可见——admin 的可见性谓词直接返回全量（`scenario_query.py:56-64`，`visibility_clause` 对 admin 返回 None）。用例量上来后，admin 打开「我的场景」页（现状查询 `visibility=private`）看到的是**全员的** private 场景，自己的用例淹没在里面。这不是权限漏洞——admin *能*看全部是矩阵拍板过的——是**默认镜头**放错了档位。
2. **共享只有 fork**。跨人协作的两条现通道：发布公共库（全员可见，粒度过粗）、handoff 分发（`routers/handoff.py`，明确「分发 = Fork 副本，不是授权」——副本从此漂移，原件更新不同步，发送方零控制权）。「把这一批回归用例给同事跑」这个最普通的协作动作没有正解。
3. **批量执行没有实体**。`Execution.batch_id` 是纯归并键（`models/execution.py:53-58` 注释：「批只是归并键，没有批级执行策略」）；「挑 N 条一起跑」目前是前端 `Runner.vue` 的临时队列（逐条 `await` 发起、客户端生成 batchId），选出的集合不落库、不可复用、不可共享。

## 1. 架构总纲

### 1.1 权限三问分层（本方案的总框架）

权限系统实际在回答三个正交问题，混在一起就会用权限系统去解偏好问题（痛点 1 的病根）：

| 问题 | 属于 | 机制 | 本方案动作 |
|---|---|---|---|
| 我能做哪些平台操作 | **政策** | 三级 RBAC（`require_role`，一期已落地） | 不动 |
| 我能看到谁的内容 | **政策** | 单一判定式 `public OR owner=:me OR admin`（§4.5 扩展） | 加一个组授权谓词 |
| 我默认以什么视角浏览 | **偏好** | 前端镜头（我的 / 全部），不入权限系统 | 新增（§6） |

「admin 看到海量用例」整体属于第三问。它不是权限漏洞，是镜头默认值挂在了第二问的 admin 分支上——修镜头，不动矩阵。

### 1.2 既有四原则的沿用

《权限一期》§0 四条原则全部继续有效：权限是政策不是偏好（镜头不违反——镜头改变的是**我浏览什么**，不是**谁能看到什么**，见 §6.3 边界论证）；运营看信号与字段面不看值面；前端守卫只是 UX；判定式单点收敛。《join-projection 口径统一》G5 定下的可见性谓词标准式随本文扩展（§4.5），security_invoker 视图同步更新。

### 1.3 新原则五：治理权 ≠ 内容镜头

admin 角色里捆绑着两件事：**治理操作权**（下架、离职处置、适配运维、审计、用户管理）与**默认内容全知**。代码库既有设计已经在拆这个捆绑——执行记录对 admin 硬隔离（一期 §1.2 刻意不变量）、凭证连 admin 都不可见（一期 §2.1）——方向早已是「admin 是运营特权，不是全知」。本方案把这条说破为显式原则：**admin 的权力通过定向流程行使（audit、处置三选一、适配影响面），内容浏览镜头对所有人（含 admin）默认「我的」，「看全部」是一个显式动作**。场景库是「环境态全知」的最后一块，本原则把它收掉。

### 1.4 范式决策：不换代数

为排除「有没有整体更好的权限模型」，逐案否决（论证详见评审讨论，此处存结论）：

| 候选范式 | 否决理由 |
|---|---|
| 细粒度 RBAC（角色→权限包→资源） | 三级角色十余种资源，0011 已证明改角色语义成本极低；权限间接层换来的灵活性无人消费 |
| ReBAC（Zanzibar/OpenFGA 元组） | 列表端点全要 SQL 分页+可见性过滤，引擎喂不饱 SQL，最终仍要把元组拼回 WHERE——双份维护；plate 内网受信、CLI 走 git 身份，全系统只有一个鉴权执行方，共享判定的核心收益落不了地 |
| ABAC / 策略引擎（OPA/Cedar） | 规则实际很简单（一列 visibility + 属主 + 角色）；「策略在外、过滤在 SQL」双轨维护 |
| 团队/组织层级（org→team→repo） | 单团队部署用不上；owner_id→team_id 是全表归属迁移；树形隐含单归属，与「一个回归用例同时属于冒烟集和回归集」的真实用法相悖 |

**演进触发器**（何时回来重评，一条都没响之前不动）：出现第二个鉴权执行方（plate 不再满足内网边界 / CLI 需平台身份）→ 集中式判定服务；真实多团队 → 组 owner 允许是团队或引入层级；条件化规则需求（时间窗/环境限定）→ ABAC；直连 psql 的数据面泄露成为实际风险 → RLS 重档（既有拍板 defer 不变）。

## 2. 需求与目标态一句话

新增**场景组**（下称「组」）：组主把自己名下的一批场景归入组，可**一次授权**给指定用户（读 + 跑），可**整组批量执行**；同时把场景库浏览镜头改为默认「我的」、admin 显式切「全部」。组是**唯一**新增的 ACL 原语——不做 per-场景共享（维持既有否决）。

## 3. 翻案声明（对《权限一期》的两处窄化修订）

本方案显式修订两处既有拍板，修订面收窄如下：

1. 《权限一期》§0.5「小团队不做 per-user 授权」与 §4.2「共享（per-user 授权）不做」；handoff v2 方案否决 `scenario_shares` 授权表。
   **修订为**：不做**场景粒度**的 per-user 授权（否决继续成立——N 场景 × M 用户的授权蔓延、TTL/撤回状态管理，收益撑不起复杂度，理由原文依然成立）；**开一个组粒度的例外**：授权对象是组不是场景，一行 grant 覆盖 N 个场景，且捆绑批量执行与用例组织两个独立价值。组内场景的可见性判定仍是一条 EXISTS 谓词（§4.5），不退化成「join 共享表的组合问题」——这是当年否决的技术理由，组粒度不触发它。
2. 《权限一期》§2.2「用户可控的可见性选项收敛为一个（发布/下架）」。
   **修订为**：**对外可见性**（谁能看到我的内容）仍然只有发布/下架一个开关，此条不翻；组授权是**定向协作通道**（我指定的人能读能跑我的场景），语义上更接近「受控的工作分配」而非「公开可见性」。口径上明确：组授权不改变场景的 visibility 列，公共库/我的场景页的既有语义不受影响。

## 4. 场景组设计

### 4.1 数据模型（一次迁移，三张表）

```
scenario_groups(
  id            BIGSERIAL PK,
  name          VARCHAR(128) NOT NULL,
  description   VARCHAR(512) NOT NULL DEFAULT '',
  owner_id      INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,  -- 组主注销 → 组删除(场景不动,授权随之蒸发)
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
)
UNIQUE (owner_id, name)                    -- 同组主组名不重

scenario_group_items(
  id            BIGSERIAL PK,
  group_id      BIGINT NOT NULL REFERENCES scenario_groups(id) ON DELETE CASCADE,
  scenario_id   VARCHAR(128) NOT NULL REFERENCES composer_scenarios(scenario_id) ON DELETE CASCADE,
  sort          INT NOT NULL DEFAULT 0,    -- 组跑的默认顺序
  added_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (group_id, scenario_id),
  INDEX (scenario_id)                      -- 反查「场景在哪些组」(删除/下架提示用)
)

scenario_group_grants(
  id              BIGSERIAL PK,
  group_id        BIGINT NOT NULL REFERENCES scenario_groups(id) ON DELETE CASCADE,
  grantee_user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,   -- 被授权人注销 → grant 自收
  granted_by_name VARCHAR(128) NOT NULL,   -- 快照,人走字留(与 audit_logs/owner_name 同款纪律)
  granted_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (group_id, grantee_user_id),
  INDEX (grantee_user_id)                  -- §4.5 判定式 EXISTS 的驱动面
)
```

级联语义一览：场景删除 → item 自动出组（FK CASCADE，与 `user_stars` 同款）；组删除 → 授权全部蒸发、场景毫发无损；组主注销 → 组随之删除（**不进**删除处置三选一——组是授权的载体不是内容本体，场景处置仍走一期 §4.3 流程；若未来确有「组是团队资产需转让」的需求再议，见 §11）；被授权人注销 → 该 grant 自收。

数量上限（防 sprawl，同 `STAR_CAP=20` 的服务端 409 纪律）：每人组数 `GROUP_CAP=50`；每组场景数 `GROUP_ITEM_CAP=100`；一次组跑最多 `GROUP_RUN_ITEM_CAP=50`（§5）。取值进 `core/config.py`，可调。

### 4.2 安全边界：组内只能放组主自己的场景（一刀切，admin 无豁免）

**唯一真正的安全设计点。** 若允许组主把他人场景拉进组再授权出去，组就变成越权外泄通道（借组跑他人 private 场景、读他人 draft）。规则：`POST /groups/{gid}/items` 校验 `scenario.owner_id == group.owner_id`，不满足一律 404（不泄露存在性）——**对 admin 同样生效**：admin 可见的他人场景不经组流向第三方（admin 自己跑他人场景是矩阵既有权力，但「admin 经组把 A 的内容洗给 B」是新开的通道，不开）。admin 要让 B 跑 A 的场景，现状没有这个通道，本方案也不开（真有此需求走发布公共库，由 A 自己决定）。

### 4.3 授权闭包：grant 覆盖场景本体 + 子资源读 + run 闸

数据集与运行方案的门禁挂在父场景的 `ensure_owner` 上（`routers/run_schemes.py:33-34`、`routers/data_sets.py:56`）。若组授权只覆盖场景本体，被授权人能读定义却读不了方案和数据集，组跑直接残废。闭包显式定义：

- **读**：场景详情、draft、preview-plate、其 data sets 与 run schemes 的读端点，全部走扩展后的 `can_read_scenario`（§4.5）；
- **跑**：`POST /api/runs` 的闸从 `ensure_owner` 升为 `can_run_scenario` = 属主 ∨ admin ∨ 组授权（§5.3）；
- **写**：一概不动——场景本体、方案、数据集的写权仍属主（或 admin）only。被授权人是读者/执行者，不是协作者（协作继续走 fork 或将来真有需求再议）。

### 4.4 不变量（四条，全部承一期）

1. **凭证永不跟随**：被授权人执行组内场景时按**执行者本人**凭证池解析（`run_dispatcher._resolve_exec_auths` 本就按 owner 过滤，零改动）——延续一期 §4.1「数据可传递、凭证永不跟随」契约。
2. **执行台账属主硬隔离**：被授权人跑出的 Execution 归被授权人；组主的场景被谁跑了，组主不知道也不该知道（对 admin 同样不可见，一期刻意不变量原样）。场景 owner 侧无任何通知。
3. **public 场景的 run 闸不放松**：handoff 评审已否决「公共场景直接放开 run」（会连带放宽数据集读闸）。组授权只作用于组内（组主自己的）场景，公共库行为零变化。
4. **撤回即时生效**：grant 判定与 role 同款纪律——不进任何 token/缓存，每请求查库；DELETE grant 后下一请求即失效。

### 4.5 判定式扩展（三处同步，一处不改都不算落地）

```
can_read(user, scen) ≡
    scen.visibility = 'public'
  ∨ scen.owner_id   = user.id
  ∨ user.role       = 'admin'
  ∨ ∃ g ∈ scenario_group_grants, i ∈ scenario_group_items:
        g.group_id = i.group_id ∧ i.scenario_id = scen.scenario_id
        ∧ g.grantee_user_id = user.id ∧ g.grantee_user_id 的用户 is_active
```

（grantee 注销由 FK CASCADE 自收，谓词里的 is_active 是双保险，可省。）落地位置：
- PG 路径：`scenario_query.visibility_clause` 加 EXISTS 子查询（admin 分支维持 None——admin 全量可见不受组影响）；
- SQLite 兜底路径：`routers/scenarios.py:474-496` 的逐行 `can_read_scenario` 自动随 `_ownership.py` 的改动静默同步——但需补测试钉住；
- security_invoker 视图：`join-projection` G5 标准式更新为含组谓词的版本。

单场景对象级判定收敛在 `app/routers/_ownership.py`：`can_read_scenario` 扩展；新增 `can_run_scenario`（§5.3）。**禁止**在各 router 里散落自写组判定。

### 4.6 grant 形态：一档（读 + 跑）

只做一档授权，不做只读档、不做可再授权档（二次分发限制维持 iteration-batch 的范围外拍板）。被授权人对组的能力面：看组内容（场景摘要 + 定义）、逐个跑、整组跑；不能：改组、加减场景、改授权、改场景/方案/数据集。选人器复用现成的 `GET /api/users/roster`（CurrentUser、仅活跃、排除自己、上限 200，一期 §5.3 落地）。

## 5. 组批量执行

### 5.1 路线拍板：服务端循环 dispatch + batch_id 归并

组跑 = `POST /api/groups/{gid}/run`：服务端按 `sort` 遍历组内场景，逐个走 `run_dispatcher.dispatch_run`（复用全部既有校验：数据集/注入条目/step_to/`MAX_RUNS_PER_EXECUTION=200`），共享一个服务端生成的 batch_id。**不引入批级执行策略**（串行/并行/失败即停）——与 `models/execution.py:53-58` 及 Runner 页脚「哪些用例一起跑将来归套件」的既有拍板一致：批是归并键，批级策略归执行器侧 suite 线（见 §11 留口）。

失败语义与 `Runner.vue:457-501` 现行为对齐：**单条 dispatch 失败（校验不过/场景被删）跳过并收集，不连坐**。响应：

```
{ "batchId": "...", "started": [executionId...], "skipped": [{"scenarioId": "...", "reason": "..."}] }
```

上限 `GROUP_RUN_ITEM_CAP=50` 超出即 409。并发无需新设计：`EXEC_WORKERS=1` 的持久化 FIFO 队列天然把 N 条排队串行消化（`execution_queue.py`，PG `FOR UPDATE SKIP LOCKED`）；调大 worker 数即并行，与单发执行同池无特权。

### 5.2 已就绪、零改动的下游

`GET /api/executions?batch_id=` 批次过滤与批次 chip（`ExecutionsList.vue`）、`execution_finished` 通知按批 upsert 聚合（「批次 X：48 通过 / 2 失败」，partial unique `(user_id, type, batch_id)`）——组跑天然是一批，通知/列表/深链全复用。

### 5.3 run 闸改造

`routers/runs.py:62-69` 的 `ensure_owner` 换为 `can_run_scenario(user, scen)`（§4.3）。**注意**：rerun 路径（`executions.py:570-577`）走的是执行属主 + 场景 ensure_owner，同样换闸——被授权人 rerun 自己的执行记录、组主 rerun 自己的，各归各位。

### 5.4 必须顺手修的洞：graph 链授权缺口

`graph_dispatch.resolve_graph_units`（`graph_dispatch.py:37-70`）对多场景链的 unit 场景**只查存在性、无归属/可见性检查**——现状任何登录用户可以经 graph 编排跑他人 private 场景，这是与组同构的既有缺口。P1 强制收口：`materialize_graph` 物化每个 unit 时对发起人逐个过 `can_run_scenario`，不满足抛 `GraphDispatchError`（路由层 4xx，404 口径不泄露存在性）。

### 5.5 组与 graph/suite 的关系（正交，不映射）

组是**稳定集合**（组织 + 授权载体），graph 是**一次性编排**（compose/chain/gates）。组不映射为 GraphSpec；将来 suite 线成熟后，组可作为 suite 成员来源**导出**（留口不实现，见 §11）。

## 6. 浏览镜头（scope）

### 6.1 后端

`GET /api/scenarios` 增 `scope ∈ {mine, all}`，**默认 `mine`**：

- `mine` → `owner_id == :me`（我创建的全部，**含已发布**）；
- `all` → 现行可见性上限（admin = 全量；其他 = public + own）。非 admin 传 `all` 静默等价于其上限，不报错（前端无需分支；`all` 对非 admin 与公共页集合本就近似重合，前端不提供入口即可）。

改 `scenario_query.visibility_clause`（admin 分支在 `scope=mine` 时加 owner 条件）与 SQLite 兜底两处。

### 6.2 前端与页面语义的顺手修正

「我的场景」页改查 `scope=mine`：owner 会看到自己的 public 场景也列进来（现状只列 private，发布后自己的用例在「我的」页失去踪迹，是既有体验缺陷）。行内加 public/private 徽标，发布/下架管理入口随之收敛到一处。`RunnableScenariosCard` 的派生口径（现 `visibility !== 'public'` 判 mine）同步改为按 owner 判定。admin 的「全员视角」= 场景库一个显式开关（仅 admin 可见）→ `scope=all`；「公共场景」页维持 `visibility=public` 不变。`scenario_filter_groups`（bucket=mine|public 的筛选组偏好）键空间不动，镜头是查询参数不是桶。

### 6.3 与原则一的边界论证

「权限是政策不是偏好」反对的是把**可见性政策**做成个人开关（「我的执行记录对谁可见」）。镜头改变的是**我自己浏览什么**，不改变**谁能看到什么**——任何人的 `scope=all` 拿到的集合与其可见性上限严格一致，矩阵一个字没动。镜头是偏好层的排序/过滤同族物，归前端与查询参数，不入权限判定。

## 7. 权力矩阵增量（对一期 §2.1 的 diff 行）

| 资源 | 归属者（组主） | 被授权人 | 其他 user | member | admin |
|---|---|---|---|---|---|
| 组（本体：改名/删除/加减场景/改授权） | 全权 | ✗ | ✗ | ✗ | 全权（治理，同场景 admin 面口径） |
| 组（读：组内容/场景摘要） | ✓ | ✓ | ✗ | ✗ | ✓ |
| 组内场景（读：定义/draft/方案/数据集） | 既有全权 | **✓（闭包 §4.3）** | ✗ 404 | ✗ 404 | 既有 ✓ |
| 组内场景（写） | 既有全权 | **✗（不变）** | ✗ | ✗ | 既有 ✓ |
| 组内场景（跑/组跑/rerun 自己的执行） | 既有 ✓ | **✓（新开，唯一新通道）** | ✗ | ✗ | 既有 ✓ |
| 执行记录 | 归执行发起人 | 归执行发起人 | — | — | owner 硬隔离（**不变**） |
| 组跑产生的批次通知 | —（组主无感知） | 按 batch_id 聚合（既有机制） | — | — | — |

一期 §2.1 矩阵其余各行原样有效。特别注意「组内场景（跑）」是被授权人唯一的新增能力面——它就是需求的本体，也仅此一格。

## 8. 通知与审计口径

- **通知**：新增 type `group_shared`（被拉进组/被新增授权时通知被授权人，带组深链），进通知中心与按 type 偏好开关（既有机制自动覆盖）。**取消授权不通知**——owner 动的是自己的资源（与「admin 下架他人场景须通知原作者」不同：那是 admin 动**他人的**资源）。组跑完成通知 = `execution_finished` 按 batch_id 聚合，零新增。
- **审计**：grant/revoke/组 CRUD **不入 `audit_logs`**——维持「只记特权写 + 用户管理写」口径；组主对自己资源的授权同「发布 public 不入审计」一类。组的创建/授权事件入 `activity_events` 时间线（业务过程记录，既有机制）。
- **服务画像**：画像信号层维持平台视角不按 owner 过滤（服务画像方案 §2.4 槽③既有拍板），镜头只作用于场景库列表，两处口径互不影响。

## 9. API 与 plate 管道

### 9.1 端点清单（platform.groups.*）

```
GET    /api/groups                     # ?scope=mine|shared(两者分节返回;admin 可加 all)
POST   /api/groups                     {name, description}                  → 201
GET    /api/groups/{gid}               # 详情:items(场景摘要)+grants(名册摘要)
PATCH  /api/groups/{gid}               {name?, description?}
DELETE /api/groups/{gid}               # 组删除,场景不动
POST   /api/groups/{gid}/items         {scenarioId}                         # §4.2 属主校验
DELETE /api/groups/{gid}/items/{scenarioId}
PUT    /api/groups/{gid}/grants        {userId}                             # 幂等 upsert + group_shared 通知
DELETE /api/groups/{gid}/grants/{userId}
POST   /api/groups/{gid}/run           # §5.1 组批量执行
```

对象级权限：组 CRUD/items/grants = 组主 ∨ admin；组读 = 组主 ∨ 被授权人 ∨ admin；组跑 = 组主 ∨ 被授权人 ∨ admin。错误口径沿用仓规：不可见 → 404，可见不可写 → 403。分页信封与字段投影按 M4 既有口径。

### 9.2 plate 侧配套产出（批次 E 同款管道）

按「管理员管理成员」切片的既有流程：`systems/platform/deliverables/prd-group-sharing.md`（PRD）→ `story-owner-shares-a-group.md`（故事）→ `dictionary/group.md`（词条：`entity:scenario_group`、`cap:group.share`、`cap:group.run`、`outcome:group.shared`）→ `systems/platform/endpoints/platform.groups.*.md`（上表逐端点）→ 评审入库 → 渲染进 catalog。**字典与端点描述的角色词一律用新口径（user/member/admin）**——与 §12 的 0011 收尾债同步清偿。

## 11. 明确不做（否决史）

| 项 | 理由 |
|---|---|
| per-场景共享授权表 | 一期 §0.5 否决维持，§3 窄化只开组粒度 |
| grant 多档（只读/可再授权）、二次分发 | 一档够用；再授权 = 权限蔓延的入口 |
| 组嵌套 / 团队层级 / org 模型 | §1.4；单团队无此问题 |
| 公共组 / 组发布 | 组是定向协作通道，公共可见性已有公共库，不造第二概念 |
| 批级执行策略（串行/失败即停） | 既有拍板：批是归并键，策略归 suite 线 |
| 组映射/导出 GraphSpec | 稳定集合与一次性编排正交（§5.5）；导出留 P2 口 |
| 组转让（处置三选一加第四选） | 组随组主 CASCADE；真有团队资产需求再议 |
| RLS 重档 / ReBAC / ABAC / 策略引擎 | §1.4 触发器未响 |
| 镜头入权限判定 / 「全部」落审计 | 镜头是偏好不是政策（§6.3）；admin 全量可见本就是矩阵拍板 |
