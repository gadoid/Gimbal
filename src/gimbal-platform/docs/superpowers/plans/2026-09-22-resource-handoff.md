# 资源分发(Handoff)设计方案 — 待评审

> **用途**:用户隔离下的点对点资源分发能力。沉淀 2026-09-22 评审对话:
> public 中转之痛(库臃肿/复制分叉/忘记回收)→ 分享语义裁定(交接=
> fork 副本)→ 泛化为多资源分发 → 范围确认(维持现规则,执行记录不做)。
> **状态**:待评审。§7 决策点为全部待拍板项。
> **配套**:权限域语义见 `用户权限与用户管理-设计方案`;本轮读侧基础
> 见 `2026-09-22-join-projection-and-caliber-unification.md`(已实施)。

## 0. 背景与问题

用户隔离把资源锁在 owner 名下后,协作只剩两条路,各有硬伤:

* **public 中转**:A 发布公共 → B 复制自取 → **A 忘记下架**,公共库被
  当传输介质,越来越臃肿;且 B 拿到的是 fork,A 修复后 B 跑旧版(版本
  漂移)。
* **admin 越权代看**:不可持续,也不解决"B 要自己跑/自己改"。

需求陈述(评审原话):一个人想用另一个人写的用例执行,或**基于该版本
再做调整**;且不止用例 —— 常量等隔离资源同样需要"快速分发"。

## 1. 语义定稿:分享 = 交接(fork 副本),不是授权(live-link)

评审裁定(2026-09-22):

* 分享的语义是"**我基于这个版本再做调整**"——受让人要的是一份归自己
  的副本,漂移是本意不是缺陷;
* "只读跑一次"不需要分享概念(让 owner 跑或走公共即可);真出现高频
  "非 owner 直接执行"需求时,另立运行授权,不与分发捆绑;
* 由此,**不做授权表、不做 TTL、不做共享状态管理**:发起方分完即无
  后续负担(治"忘记回收"——根本没有可忘的东西),接收方落地即 owner。

对照被否掉的方案(记录取舍依据):

| 方案 | 否因 |
|---|---|
| `scenario_shares` 授权表 + 谓词扩展 + TTL | 解决"共享维护一份",非本需求;授权状态要管理,TTL 治标 |
| 公共场景直接执行(放开 run 闸) | 要连带放宽数据集读闸,推翻一条已评审的跨用户泄露收紧 |

## 2. 范围矩阵(评审确认版)

| 资源 | 结论 | 说明 |
|---|---|---|
| **场景(含全部数据集 + 方案)** | **一期做** | 复用 `copy_scenario` 深拷;副本 private 归受让人;meta 记 `sourceScenarioId` 溯源 |
| **常量池条目** | **一期做** | 拷行切换 owner;同名(owner+name 唯一)**跳过并报告** |
| 凭证(auth_sessions) | **二期,单独拍板** | 密文整行复制 = 给用不给看(平台执行时才解密铸 token);但"任意用户可转账号使用权"是安全姿势变化,等分发机制跑通后再拍 允许/永不(永不 = 共享注入只走 operator 的 carry/别名) |
| 执行记录 | **不做(本轮确认)** | 维持 §5.1 硬隔离,连 admin 也无旁路;要给人看用导出快照 |
| board 卡 / 服务画像 | 无需 | 本就全局可读(他人只读) |
| carry 值表 / 服务别名 | 不属此列 | 全局技术资产(operator+ 管理),它们本身是共享层 |
| ~~查询视图~~ | **勘误移除** | 核实为 plate 侧共享目录代理(`routers/query_views.py`),非用户隔离资源 |

## 3. 交互设计

发起方(以 Alice 分发场景给 Bob/Carol 为例):

1. **入口**:场景库列表行操作菜单"分发…"(与 发布/复制/删除 同级,
   详情页头部同给);常量池条目行"分发"。
2. **分发对话框**(统一 `HandoffDialog`,不随资源变形):
   * 上半资源摘要:场景名 + "含 N 数据集 · M 方案"(常量/凭证实名);
   * 选人:前缀实时搜索(名册端点),多选 chip——"快速分发"的手感来源;
   * 留言(可选,≤200 字,进接收方通知正文);
   * 确认按钮带计数:"分发给 N 人"。
3. **提交与逐人结果**(同步单请求,响应原地翻成结果面板):
   ```
   ✓ 张三  已分发(新场景 sc-order-main-copy-a1b2)
   ⚠ 王五  跳过:他已有同名常量 "order_env"
   ✗ 李四  失败:账号已注销
   ```
   冲突策略 = **跳过并报告**,绝不静默覆盖;单人失败不影响他人。
4. Alice 到此为止:原件纹丝不动,无共享状态、无待回收授权;再给两人,
   重复一次即可(每次新副本新 id)。

接收方(Bob):

1. **站内通知**(照 `resource_transferred` 先例):"Alice 分发给你场景
   《下单主链路》(含 3 数据集、2 方案)"+ 留言,深链直达;
2. 副本已落在**他自己的**场景库(private,他就是 owner):改/跑/配方案
   一切如常;列表行与详情页带轻量"**分叉自 sc-order-main**"标记;
3. **级联自然成立**:Bob 可把改好的副本再分发给 Carol —— 权限跟着
   所有权走,无需额外机制。

边界(交互的一部分):不带走执行历史;不带凭证(二期前,场景依赖凭证
时 Bob 首跑见既有"缺凭证"引导);副本恒 private,发布与否 Bob 自定。

## 4. 后端设计

### 4.1 接口

```
POST /api/handoff
{
  "resource_type": "scenario" | "constant",     // 二期 + "auth_session"
  "resource_id": "sc-order-main" | 42,
  "target_user_ids": [2, 3, 5],
  "message": "…"                                  // 可选
}
→ 200 { "results": [
    {"user_id": 2, "user_name": "张三", "status": "delivered",
     "new_resource_id": "sc-order-main-copy-a1b2"},
    {"user_id": 3, "user_name": "王五", "status": "skipped",
     "detail": "已有同名常量 order_env"},
    {"user_id": 5, "user_name": "李四", "status": "failed",
     "detail": "账号已注销"} ] }
```

* 发起权限 = **资源 owner**(admin 可代发,与 `ensure_owner` 口径一致
  ——见 §7 决策点 2);非 owner 403,资源不存在 404;
* 目标含发起人自己 → 422(无意义);全部目标失败仍返回 200 + 逐人结果
  (整体事务性:逐人独立提交,一人失败不回滚他人——分发是幂等可重试的
  独立副本,不值得整批原子)。

### 4.2 Adapter 契约

每资源一个 adapter,职责三件:深拷、目标空间冲突判定、结果行构造。

| adapter | 实现 | 冲突面 |
|---|---|---|
| scenario | `copy_scenario(scenario_id, new_owner, new_owner_id, *, source_meta=…)` —— 现函数已参数化 owner,加 `meta.sourceScenarioId = 原 id`(用户可见溯源) | 无(副本恒新 id `-copy-<hex>`) |
| constant | 拷行:`owner_id` 切换、`updated_by` 记发起人 | `uq_constant_owner_name` 同名 → skipped |
| auth_session(二期) | 拷行:密文原样(`FERNET_KEY` 全局同钥,无需重加密)、owner 切换 | `uq_auth_owner_alias` 同 alias → skipped |

### 4.3 名册端点(member 可用,解决选人)

```
GET /api/users/roster?q=张     → { items: [{id, display_name, username}] }
```

`CurrentUser`;前缀匹配 display_name/username;上限 20;**不回角色/状态
以外的任何字段**。枚举面评估:display_name 本就在执行台账对全员可见
(owner_name 列),username 同台可见,泄露面增量 ≈ 0。

### 4.4 通知与审计

* 通知:`resource_handoff` 类型逐人送达(复用通知五表;深链按资源类型
  路由);留言进 body;
* 审计:`audit_logs` 记一条 `action="handoff"`,`detail` 携带
  `{resource_type, resource_id, targets: [...], results 摘要}` ——
  "谁把什么分给了谁"全链路可查;常量/凭证的溯源**不落资源本体**,
  靠审计(场景除外,meta 有 sourceScenarioId)。

## 5. 数据与结构影响

**零 DDL、零 alembic revision、零权限谓词改动。**

* 副本就是普通行(scenario/constant 均既有表);
* 溯源:场景进 payload.meta(既有可写源,无新列);其余靠 audit_logs;
* 与 0005/交互字段轮零依赖,可独立上线、独立回滚(纯代码回退);
* 台账语义不受影响:Bob 跑副本产生的执行记录归 Bob(§5.1 维持)。

## 6. 安全口径

* 名册枚举面:如上,增量 ≈ 0;
* 分发不含凭证期间,账号共享仍只有 operator 的 carry/别名一条正路;
* 无共享状态 = 无"授权悬挂"风险面(过期/回收/泄漏均不适用);
* 全链路审计;越权(非 owner 发起)403、404 口径与 `_ownership` 一致。

## 7. 决策点(待评审拍板)

1. **凭证二期边界**:允许交接(审计兜底)vs 永不(共享注入一律走
   carry/别名)。建议:等一期用起来再拍。
2. **admin 代发他人资源**:建议允许(与 `ensure_owner` 的 admin bypass
   同口径);若不允许,首期仅 owner。
3. **场景副本命名**:保持原名(id 带 `-copy-<hex>` 已可区分)——
   与既有 copy 先例一致,建议不改。
4. **留言上限**:建议 200 字(通知 body 为 Text,纯展示)。
5. **同目标重复分发**:允许(每次新副本);常量同名恒 skip。是否需要
   "已分发给他"提示(读 audit)——建议不做,避免暗示共享状态。

## 8. 测试清单

* adapter × 3 态:delivered / skipped(同名)/ failed(目标注销);
* 多目标混合结果(互不污染);逐人独立提交语义;
* 权限:非 owner 403、不存在 404、admin 代发(按决策点 2)、目标含
  自己 422;
* 场景深拷完整性:数据集/方案随拷、`sourceScenarioId` 落 meta、副本
  private;
* 通知逐人送达 + 深链;审计 detail 完整;
* 级联:Bob(受让人)再发给 Carol;
* 名册:前缀搜索、上限 20、字段最小集;
* 前端:对话框三态(选择/结果/错误)、入口菜单项、溯源标记展示。

## 9. 分期

* **一期**:handoff 服务 + 场景/常量两 adapter + 名册端点 + 通知/审计
  + `HandoffDialog` 与两处入口;
* **二期**:凭证 adapter(决策点 1 拍板后);
* **缓议**:执行记录只读分享(动 §5.1,须独立评审,本方案不预埋)。
