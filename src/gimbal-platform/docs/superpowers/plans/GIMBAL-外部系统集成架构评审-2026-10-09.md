## 3. 评审发现(拍板前需处理 / 澄清)

### E1(必修)·「token 回写复用」与「outputs 过脱敏键表」自相矛盾

风险表提出「高频登录场景可把 token 与过期时间作为输出回写复用」,而 §6 规定 outputs「使用同一张脱敏键表处理」——键表含 `token`,**token 一进 outputs 就被脱敏成 `***`,脱敏后的值无法复用**。二者不能同时成立。建议拍板:
- 方案 A(推荐):禁止 token 进 outputs/`state_vars`;复用改为执行器内存内的会话缓存(同通道同标签直接复用,不落库);
- 方案 B:`state_mapping` 允许显式标记「敏感但需保留」的字段,`state_vars` 不落 `last_outputs`(不进批量卡片接口)、存储加密、界面永不回显——实现面大,不建议。

### E2 · Webhook 触发未覆盖,应显式声明范围

roadmap 2.8-H6 是「Webhook 与定时同步」**两条腿**;本方案只做了定时(cron)。Jira/GitLab webhook 触发执行不在任何一期里。不是缺陷,但需要一行显式声明「webhook 触发不在本方案范围,后续单独立项」,否则 roadmap 读者会以为 H6 已被覆盖。

### E3 · P1 对 G2 的依赖被高估,可再瘦身

P1(保活)验收三条(周期刷新 / 变红一次 / 过期置灰)全部只需要 `last_status` + `last_run_at`,**不需要 outputs**;status 模板 S 档就是状态灯。G2 可以挪到 P2(kv/counter/list 模板才真正消费输出),或按设计原案并入 task 3c 一起做。两种切法都成立,拍板时定:若 task 3 排期尚远,建议 G2 随 P2,P1 更小更快。

### E4 · 「两条常驻通道」低估了进程管理面

现状是**每次执行拉起、用完即弃**(`gimbal_server_session` 按需 subprocess);「常驻」意味着平台要新增 server 进程池管理(启动、健康检查、崩溃重启、优雅退出)。这是 P1 里被一句话带过的最大实现量。建议拍板:
- 方案 A(推荐,第一期):**半常驻** —— 执行后保留 N 分钟(可配置),到期无任务则退出;不引入常驻池的看护逻辑;
- 方案 B:完整池管理(启动/心跳/重启),与「执行通道数量」的待拍板项一起定。

### E5 · 调度选主细节需写死:短持锁

`pg_try_advisory_lock` 是**会话绑定**锁(连接断开自动释放)。必须明确为「每轮扫描前取锁、扫描认领完即释放」的短持锁模式;若长持(启动时取一次),连接池换连接/断线后锁行为不可预期。另注明固定 lock key 常量,避免与队列/其他锁撞号。

### E6 · 数据模型应预留 suite 升级路径

决策 2 写「scenario(**之后是 suite**)渲染为卡片」,而 Suite 层重构刚收官(五步 + 收尾全部落地)。`integration_tasks.scenario_id` 现在指单场景,升级为 suite 时:`scenario_id` + `scheme_id` 两个字段会一起变(suite 的输入是 mode_config 而非单个 scheme)。建议建表时就预留可空 `suite_id` 列(或把定义引用统一为 `target_type` + `target_id`),避免二次迁移。这不是过度设计 —— suite 已是既成事实。

### E7 · 模板删除与 on_change 判定基准两处口径未定

- 公共模板可能被大量订阅,硬删 = 所有人卡片同时失效。建议:软删(置 `removed`,卡片走「已移除」态)或删除确认时列出订阅数;
- `result_policy: on_change` 的「状态变化」判定基准未定义 —— 建议明确为「`last_status` 变化 **或** 卡片投影字段(`output_mapping` 命中的字段)变化」,否则保活场景「服务恢复了但上次也是绿的」与「输出内容变了但状态没变」无法区分。

### E8 · 平台将出现两个 lifespan 循环任务

Suite 重构第 1 步已在 lifespan 挂了「草稿清理」小时级巡检;本方案再加 15 秒调度循环。建议顺手收敛为一个轻量「后台任务注册表」(每个任务声明周期与体量),避免 lifespan 逐渐长成面条。实现层面的事,不阻塞拍板。

### E9 · 实现提醒:侧栏与测试计数

集成页新增侧栏入口会动 `Sidebar` 的入口计数测试(此前多轮验收反复改过 16/15 项计数);`FunctionCard` 走「动态条目追加」则卡片市场组件也要留扩展点。记入实施清单即可。

## 5. 分期评估

P1 的选型(平台模式保活)经复核是**对的**:不依赖 G1、不依赖外部系统定义、能同时验证平台凭证/只读检查/调度/卡片四件事。两处调整建议:

1. **P1 减负**(E3/E4):G2 挪出 P1(或明确并入 task 3c);常驻通道降为半常驻。瘦身后 P1 = 表 + 系统用户 + 只读检查 + 调度循环 + runner(不写台账)+ status 卡 + 批量接口 + 集成页基础版。
2. **P2 与 plate S1.5 错峰**:P2 要动 plate(`kind` 字段是 M2 变更 + GitLab/Jenkins 系统定义批量入库)。plate 侧 S1.5a 速修与「step 分支表达式验证」建议排在 P2 动土前完成,否则 M2 变更叠在未收口的地基上。

P3(Jira 推送)的前置「执行器报告重构完成」与 roadmap task 3 一致,排期上等 task 3 出口;P4(知识类拉取 → 评审草稿)依赖 Markdown 方言,维持最后,与 plate 主线「编写 → 评审 → 入库」一致。
