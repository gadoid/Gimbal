# 用户权限与用户管理 — 设计方案

> 状态：设计稿（2026-09-20）。落地依赖《PostgreSQL迁移与后端化-设计方案》M2 的新表结构（role 列、notifications、audit_logs、user_stars 均在迁移落库时一并建成）；两份方案互为前置，本文负责权限域的目标态。

## 0. 现状与四条设计原则

### 0.1 现状一句话

全平台权限 = `users.is_admin` 一个布尔位（`app/models/user.py:14`），执行点收敛在三处依赖（`ensure_owner` / `can_read_scenario` / `AdminUser`，`app/routers/_ownership.py` + `app/core/deps.py`），场景是唯一有可见性（private/public）的资源，无通知、无共享、无审计表。用户管理页（`views/UsersAdmin.vue`）CRUD 已完备，但成员没有任何自助入口（改密/改昵称要去求管理员）。

### 0.2 原则一：权限是政策，不是偏好

哪些资源对谁可见，由角色矩阵统一规定（§2）。**不**给用户开「我的执行记录对谁可见」「我的画像信号是否上报」这类个人开关——内部平台上，可见性的口子一旦按人开，矩阵就会组合爆炸，审计也无法回答「此刻谁能看到什么」。用户唯一可控的可见性选项就是场景的 发布/下架，这个口子保留并且只保留这一个。

### 0.3 原则二：运营看信号与字段面，不看值面与全文

跨 owner 的运营视角分两层。**信号层**（服务画像的热力网格、批次计数）：状态、次数、趋势。**字段面层**（适配工作必需）：哪个场景第几步引用了哪个字段/端点——`impact()` 的逐行 (scenario_id, step_index, source, field_name) 属于这层，operator 没有它干不了活。**永远不可见的是值面与全文**：他人场景的配置定义与步骤内容、执行快照、凭证引用、适配的 `before_json`。这条「字段面可见、值面不可见」的线（第五轮修订：初稿只写「聚合信号」，与 impact() 的实际返回粒度自相矛盾）把「运维需要的全局视野」和「内容隐私」切开，是 §1 角色分级能保持简单的根基。

### 0.4 原则三：前端守卫只是 UX，后端依赖才是边界

维持现状哲学：路由 meta（`requiresAdmin`）和 `auth.isAdmin` 分支渲染只负责「别让成员点进去吃 403」，真实判定全在后端依赖里。新角色照此办理——前端改成 `auth.role` 单点收敛（`stores/auth.ts:77` 的注释本来就预留了这一天），后端把 `require_admin` 升级为 `require_role(...)`。

### 0.5 原则四：小团队不做 per-user 授权

「把我的私有场景共享给张三」不做。要共享就发布公共库（现有机制，带署名与复制语义）。理由：内部小团队公共库已覆盖需求；而 per-user 共享会把可见性判定从「一行 `can_read_scenario`」变成 join 共享表的组合问题，方案/数据集/执行记录还要跟着定义共享语义，收益撑不起复杂度。

## 1. 角色分级：三级单角色

### 1.1 为什么是 member / operator / admin 三级

现状 admin-only 的面拆开看是两类完全不同的权力：

- **技术运营权**：服务别名、字段默认值（carry）、适配处理、全站执行信号——管的是「平台资产」，不管人，也看不到他人私有内容；
- **人事与内容权**：用户管理、升降级、重置密码、全员私有场景可见、以他人身份视角发起执行——管的是「人和内容」。

合成一个布尔位，导致「只想值班处理适配的同事」必须拿到「能看所有人私有编排」的钥匙。拆出中间级 **operator（运维/值班）**，正好承接技术运营权；**admin** 保留人事与内容权。不设第四级 superadmin——末位 admin 保护已存在（`users.py:265-283`），超级管理员解决的是「admin 互相误伤」问题，在内部平台出现概率趋近于零，等真出现再加不迟（见 §8）。

### 1.2 权力矩阵（现 admin-only 面的归属）

| 现有面 | member | operator | admin |
|---|---|---|---|
| 用户管理 `/admin/users`（CRUD/升降级/重置密码/启停/删除） | ✗ | ✗ | ✓ |
| `GET /api/users` 全字段列表 | ✗（收紧，见 §5.3） | ✓ | ✓ |
| 服务信息管理 `/service-admin`（别名 CRUD） | 读面 | **团队共享别名读写；他人个人默认不可写（属主/admin）** | 读写 |
| 默认值 `/carry-config` 写面（PUT） | ✗（403） | **读写** | 读写 |
| 适配中心 admin 块（diff 检查/未索引警示/影响面/待适配卡/批次 ops） | 仅 `scope=mine` 只读 | **全量读写** | 全量读写 |
| 服务画像 grid/board（跨 owner 聚合信号） | ✓（仅信号，无配置） | ✓ | ✓ |
| 线索板卡片 `board_cards` | 全员读/作者写 | 同 | 同 |
| 他人 **private** 场景定义 | ✗（404） | **✗（原则二）** | ✓ |
| 「我的场景」页全员私有视角（`ScenariosMine` admin 副标题） | ✗ | ✗ | ✓ |
| 执行器发起他人场景（`Runner` `pickerList`） | ✗ | ✗ | ✓ |
| **执行记录明细** | owner 硬隔离 | owner 硬隔离 | **owner 硬隔离（保留现状）** |
| 工作台 adminOnly 卡（aliases/carry/users） | ✗ | aliases+carry | 全部 |

注意倒数第三行：执行记录现状对 admin 也是 owner 硬隔离（`core/deps.py` 的 `get_owned_execution` 无 admin 旁路，`executions.py:73/156` 的 SQL 同样只过滤 `owner_id == user.id`）。**这是刻意的不变量，本方案显式保留**。理由收窄（第六轮：原则二改写后，`scenario_snapshot` 的场景全量定义对 admin 本就可见——矩阵里 admin 对 private 场景可见可管——不能再作为隔离依据；立得住的只剩 `config_json` 的**凭证引用面**：谁在哪个场景注入了哪些凭证别名，是包括 admin 在内的运营视角都无权也不必知道的）。admin 排查全局问题走画像聚合与批次维度，不走翻他人执行明细。

**别名的两类归属压不得一行（第七轮拆行）**：`service_aliases` 混着团队共享（`owner_user_id` 空）与他人个人默认（非空），且 create/patch 的 `owner_user_id` 是可写入参（`routers/service_aliases.py:34/46/73`，现状整面 admin-only）——operator 若可写他人个人默认、甚至把它转到自己名下，就是人事/内容权掉进技术运营角色，与 §1.1 拆三级的立论相反。改造时 operator 面收紧为「共享别名可写、**归属字段不可改**」；他人个人默认的写权只属属主与 admin。

**读写不对称的显式不变量（第五轮补，已回读核实）**：适配的 apply 与 rollback 最终都落 `scenario_store.update(db, snap.entity_id, …)`（`adaptation_service.py:906-908` 及回滚路径）——operator **写**他人 private 场景的 payload，却始终**没有**该场景的读权。这个不对称是刻意设计：适配写入由字段级 op 驱动（改哪个字段、从什么变到什么），operator 永不获得场景全文；`before_json` 是内部回滚数据，**永不出 API**——现状 `SnapshotRef` 只返回 entityType/entityId（`schemas/adaptations.py:121-125`），场景全文没有泄露面。补一条出参 schema 白名单测试钉死这条边界：否则将来有人为做「回滚预览」把 `before_json` 开出去，边界就无声破了。

### 1.3 落库与判定

- `users` 表新增 `role VARCHAR(16)`，取值 `member|operator|admin`。**过渡形状（第八轮定「方向翻转」）**：M2 切换时 role 建为 is_admin 的 STORED 生成列（`CASE WHEN is_admin THEN 'admin' ELSE 'member' END`——`is_admin=true → 'admin'` 的映射即表达式自算，代码零读零写，回滚到无 role 列的旧 SQLite 库物理上不可能炸，迁移方案 §3.3 回滚）；M2.5 `ALTER COLUMN role DROP EXPRESSION` 转可写、权威翻转为 role，`is_admin` 列保留一个过渡版本（读侧由 `role` 派生），下个版本删除。
- 后端新增依赖工厂 `require_role(*roles)`，现 `require_admin` 改为其别名；`_ownership.ensure_owner` / `can_read_scenario` 签名不变，内部 `user.is_admin` 改为 `user.role == 'admin'`。
- **role 不进 JWT**：`get_current_user` 本来就每请求查库（`core/deps.py:18-32`），role 从库里取，保证**后端**升降级即时生效，不引入「token 里角色过期 60 分钟」的窗口。
- **「即时生效」的前端限定（第六轮补）**：`stores/auth.ts` 把 currentUser（含角色位）快照进 localStorage，降级后本地菜单要到下次 `fetchMe` 才收敛。既然铃铛已定 30s 轮询，让 `unread-count` 顺带回传一个角色版本号（`users.updated_at` 即可），前端发现变了就 refetch me——几乎零成本补齐前端即时性。
- 前端 `stores/auth.ts` 的 `isAdmin` computed 扩展为 `role: Ref<'member'|'operator'|'admin'>` + `hasRole(...roles)`，所有 `is_admin` 分支渲染点（AdaptationCenter / Runner / ScenariosMine / 工作台卡片注册表 / Sidebar adminOnly 过滤）改用 `hasRole`；路由 meta 从 `requiresAdmin` 泛化为 `requiresRoles: string[]`。
- 角色 JSON 序列化：`UserPublic` 增加 `role`，`UserPatchIn` 的 `is_admin` 布尔换成 `role` 枚举；末位 admin 保护同步改为「不可降级最后一个 admin」；`/auth/me` 的 `MeOut` 包裹 `UserPublic`（`auth.py:138-140`），role 自动随身份接口下发，无需单独改。

## 2. 可见性矩阵与用户可控选项

### 2.1 资源 × 角色 全矩阵

| 资源 | 归属者 | 其他 member | operator | admin |
|---|---|---|---|---|
| 场景（private） | 全权 | ✗ 404 | ✗ 404 | 可见可管 |
| 场景（public） | 全权 | 读 + 复制 + 验证执行 | 同左 | 同左 |
| 数据集 / 运行方案 | 随场景 | 同场景可见性 | 同场景 | 同场景 |
| 凭证 `auth_sessions` | 全权（密文） | ✗（引用计数可见、私有引用仅计数不显名） | ✗ | ✗（**不变**） |
| 常量池 | 全权 | ✗ | ✗ | ✗ |
| 执行记录 | 全权 | ✗ | ✗ | ✗（owner 硬隔离不变） |
| 收藏/关注 | 全权 | ✗ | ✗ | ✗ |
| 服务画像信号 | — | 全员（聚合） | 全员 | 全员 |
| 线索板卡片 | 作者写 | 全员读 | 全员读 | 全员读 |
| 服务别名（团队共享，`owner_user_id` 空）/ 字段默认值 | 全局资产 | 只读 | 读写 | 读写 |
| 服务别名（他人个人默认，`owner_user_id` 非空） | 他人私有配置 | ✗（现状写面本就 admin-only） | ✗（§1.2 两类归属拆行） | 读写（含归属字段变更） |
| 适配批次 | operator/admin 处理 | `scope=mine` 只读 | 全量读写 | 全量读写 |
| 用户列表 | — | ✗（收紧） | ✓ | ✓ |

凭证行连 admin 都列 ✗ 是有意的：`GET /api/auths` 本就按 owner 过滤，`include_secrets=true` 返回明文密码（`auth_sessions.py:159-183`）——**管理员也不应该能翻他人明文凭证**，这个现状边界值得写进方案固化。（成员凭证丢失走管理员重置个人密码、凭证本人重建的流程。）

### 2.2 用户可控的可见性选项（收敛为一个）

- **场景 发布/下架**（private ⇄ public）：保留现有交互（「我的场景」行菜单 + confirm 文案），发布后全员可读定义、可复制、可验证执行，作者署名公开。
- 明确**不加**的选项及理由：
  - `unlisted`（链接可见不列出）：内部平台没有「转发链接」的社交场景，加了只会让「公共库到底有什么」变得不可审计；
  - 匿名发布：署名即问责，是内部平台的特性不是缺陷；
  - 执行信号退出画像：画像完整性是运营底线，允许个人关闭会让热力网格出现无法解释的空洞；
  - 执行记录可见性：owner 隔离是硬边界，不是偏好。

## 3. 用户间通信 → 站内通知中心（不做 IM）

### 3.1 要解决的真实痛点

通信需求在现状里已经存在，只是没有载体：

1. 成员的场景被适配批次触碰——现在要自己进适配中心才能发现（`scope=mine` 是拉的，不是推的）；
2. 发起批量执行后离开页面——跑完/跑挂了没有任何提醒，只能回来轮询列表页；
3. 管理员想广播一条平台公告（如「今晚停服迁移 PG」）——没有渠道。

这三个都是**系统 → 人**的通知，不是人对人的消息。据此拍板：**做站内通知中心，不做用户间 IM**。IM 引入在线状态、未读同步、内容审核一连串与本平台无关的负担，且「找某个同事」在内部平台走工位比走路内信快。

### 3.2 通知类型（首期四种）

| type | 触发点 | 接收人 | 默认 |
|---|---|---|---|
| `execution_finished` | run_dispatcher 终态落库时（`run_dispatcher.py:1121-1160` 收口处）；带 batch_id 的执行**按批合并为一条**（见下注） | 发起人 | 开 |
| `adaptation_applied` | 批次 ops 应用且 touched scenario 属于该成员（仅 scenario/dataset 类实体产生通知；carry_binding/carry_default 是全局资产无归属，不通知） | 各受影响 owner | 开 |
| `announcement` | 管理员在用户管理页发布（带 `expires_at`） | 全员 | 开 |
| `scenario_unpublished` | 管理员下架了他人 public 场景（admin 全员视角下的写操作，须告知原作者） | 原作者 | 开 |
| `role_changed` | admin 升降级角色后（走现成 fan-out） | 本人 | 开 |
| `resource_transferred` | 删除处置选择「转让给指定成员」时（走现成 fan-out） | 受让人 | 开 |

### 3.3 表与接口

```
notifications(
  id BIGSERIAL PK,
  user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  type VARCHAR(32) NOT NULL,
  title VARCHAR(255) NOT NULL,
  body TEXT NOT NULL DEFAULT '',
  link VARCHAR(255),            -- 站内深链，如 /executions/133?rows=failed
  batch_id VARCHAR(64) NULL,    -- 批量执行聚合通知的归并键（§3.2 批量合并）
  expires_at TIMESTAMPTZ NULL,  -- 公告的过期时刻（§3.2 已承诺，初稿 DDL 漏列），查询侧过滤
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  read_at TIMESTAMPTZ           -- NULL = 未读
)
INDEX (user_id, id DESC)
-- 批量 upsert 的并发命中面（第六轮补）：50 条批次 N 行几乎同时终态、同时 upsert 同一条通知，
-- 没有唯一约束就退化成 SELECT-then-UPDATE 的 RMW，MVCC 下直接产出重复通知行：
UNIQUE (user_id, type, batch_id) WHERE batch_id IS NOT NULL   -- partial unique，ON CONFLICT 命中面
```

接口三只：`GET /api/notifications?unreadOnly=&limit=`（信封分页）、`POST /api/notifications/read`（批量标读）、`GET /api/notifications/unread-count`（顺带回传角色版本号，见 §1.3 前端限定）。批量聚合刷新用**条件 UPDATE，且聚合计数在 UPDATE 语句内用子查询现算**（`SET body = (SELECT … FROM executions WHERE batch_id = …)`）——Python 先算好再写会在两行几乎同时终态时，被后提交的那条用更早读到的计数覆盖（铃铛永远停在「46 通过」）；`ON CONFLICT` 必须重复 partial unique 的谓词：`ON CONFLICT (user_id, type, batch_id) WHERE batch_id IS NOT NULL`——漏写是**运行时才炸**的 `no unique or exclusion constraint matching`。公告发布走 `POST /api/admin/announcements`（admin only），写入时对全员 fan-out 行（内部量级 <百人，直接逐行插入，不做懒展开）。

投递方式拍板**轮询**：顶栏铃铛 30s 拉一次 unread-count，有新才拉列表。不上 WebSocket/SSE——活跃执行页已有 1s 轮询先例，为一个铃铛引入长连接不划算（远期若迁移方案 M5 的轮询治理上了 SSE，再搭车）。

> **批量合并（第五轮补）**：批的语义是「一次挑 N 条逐条发起、共用 batch_id」——批只是归并键，没有批级执行策略、也没有批级终结点（`models/execution.py:44-49`）。跑 50 条批次若逐执行落通知 = 铃铛被 50 条刷屏，上线第一天就会被人关掉。定案：带 batch_id 的执行按批 upsert 单条通知（「批次 X：48 通过 / 2 失败」），随批内每条终态刷新，聚合口径 = 该 batch_id 下全部执行的 passed/failed 汇总——比逐条更有用且几乎零成本；无批次的单发执行才逐条。**已读语义（第六轮定）**：批次通知已读后又有新行完成，**不重置为未读**——否则一个长批次会反复戳人；新终态只刷新通知正文里的聚合计数。

## 4. 用户间数据传递

### 4.1 复制（fork）——主通道，保留

公共场景「复制到我的」深拷贝为调用者 private 副本（`scenarios.py:298-318`），**凭证模板按执行者本人池解析**（复制别人的场景，`${auth.alias.*}` 落地到自己的凭证）——这套「数据可传递、凭证永不跟随」的机制是本平台最值钱的边界之一，方案把它文档化为正式契约：任何数据传递通道（复制、转让、批次适配）都不得携带或暴露凭证密文/明文。

### 4.2 共享（per-user 授权）——不做

见 §0.5。补充一个现有机制已经覆盖 80% 场景的证据：关注（Star/Follow）支持关注他人 public 场景并看健康趋势（`ScenarioFollows.vue`），「我想持续看同事的场景」走关注 + 私信作者发布即可。关注上限 20 现在只有前端强制（`toggleStarWithCap`），收藏迁入 `user_stars` 表后由服务端 409 兜底（迁移方案 M6），口径不靠客户端自律。

### 4.3 转让与用户删除时的资源处置——新增，admin 触发

现状删除用户时**什么都没级联**（查漏轮核实，比预想更糟）：`User` 模型没有定义任何 relationship，`db.delete(target)` 只删 users 行，而 FK 从未生效（见迁移方案风险 1）——凭证、常量、执行记录、线索板卡、个人服务别名全部悬空；`stars.json` 也没有按用户清理的调用（`marks_store` 只有场景删除的 `remove_item`）。删除对话框文案「收藏一并清除，该用户上传的私有用例保留」与实际行为不符——收藏没清、私有场景也读不到。这个现状直接论证了下面的处置流程不是锦上添花，而是补一个真实缺口。

拍板改造为**删除即处置**，用户管理页删除流程增加一步（默认勾选第一项）：

1. **私有场景转公共库**（署名保留原作者字符串快照，适合「人走了，编排是平台资产」）；
2. 转让给指定成员（owner_id 批量改写，数据集/方案随场景走）;
3. 一并删除（明示二次确认）。

处置面必须覆盖的清单（随处置一并执行）：私有场景（三选一）；**个人服务别名**——`owner_user_id` 非空=个人默认、空=团队共享。模型注释明写「用户注销时置空（共享化）」（`models/service_alias.py:42-45`，FK 本就声明 SET NULL）——迁移方案对此是**显式推翻**而非「避开陷阱」：FK 从未生效、该意图从未真正执行过，且「注销即共享化」该由人显式决定；FK 改 NO ACTION（校验器）后，不处置就删用户当场报错，倒逼显式决定转共享还是删除；凭证/常量/个人别名由删除端点 Python 显式删除（**最小显式级联随 M2 切换同车（P1a，第八轮从 M2.5 拎回）**：凭证池/常量/个人别名显式删——个人别名在处置 UI 就位前取保守默认=删除，转共享是 P2 对话框的人工选项；收藏由 user_stars 的 CASCADE 自收）；**case 目录立即清扫（第六轮补）**——`data/runs/cases/<runId>/case.json` 含注入后的明文凭证（`run_dispatcher.py:635` 注释明示），平时只靠 `CASE_RETENTION_DAYS=14` 的启动期 mtime 清扫，不处置则已注销用户的明文最多还在盘上躺两周：处置时按其执行记录（executions.owner_id 定位 runId）当场清扫 case 目录，不等周期；前端「收藏一并清除」文案随本流程落地修正为实况。

配套不变量：**执行记录是审计级数据，必须比用户活得久**——`executions.owner_id` 在新表结构改为 `ON DELETE SET NULL` + 增设 `owner_name` 快照列（发起人可读的历史姓名），列表页对孤儿行显示 `owner_name（已注销）`。这条约束写进迁移方案的表设计，两文互锁。

### 4.4 请求/审批流——不做

适配批次已经是最重的「审批」场景，现状由 operator/admin 单方处理 + §3 通知受影响人，闭环成立。再引入通用审批流（申请使用某私有场景之类）与 §0.5 同理：没有真实需求支撑。

## 5. 用户管理增强

### 5.1 个人设置页（新增 `/profile`，全员）

- 改 `display_name`（走现有应用层查重 `_name_checks.py`，DB 唯一约束在迁移方案补——注意列默认值是空串，约束必须是 `WHERE display_name <> ''` 的 **partial unique**，否则两个没设昵称的用户会撞索引；应用层查重对空值跳过的语义与之一致）。**DB 约束只兜 display_name 自身的并发竞态；`_name_checks` 的 username↔display_name 双向冲突检查（冒用他人显示名 = 提权接管其资源）DB 表达不了跨列双向唯一，应用层检查不能撤**——两者并存，各管一面；

### 5.3 用户列表收紧

## 6. 审计日志（轻量）

特权操作必须留痕，否则三级角色一旦出问题无法追责。新增：

```
audit_logs(
  id BIGSERIAL PK,
  actor_id INT REFERENCES users(id) ON DELETE SET NULL,
  actor_name VARCHAR(128) NOT NULL,   -- 快照，人注销后仍可读
  action VARCHAR(64) NOT NULL,        -- user.role_change / user.delete / announcement.publish / carry.put / adaptation.op.apply / alias.write ...
  resource_type VARCHAR(32),
  resource_id VARCHAR(128),
  detail JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
)
INDEX (created_at DESC), INDEX (action, created_at DESC)
```

**只记特权写 + 用户管理写**（角色变更、删除用户、重置密码、公告、carry 写、适配 ops 应用、别名写），不记普通读、不记成员自己的常规 CRUD（自己的场景增删改不留痕——那不是特权）。查询端点 `GET /api/admin/audit-logs`（admin only，分页信封）。`adaptation_ops` 保持原样（它是业务过程记录，不是审计）。

## 7. 改造清单与分期

### P1a（与迁移方案 M2 停服窗口同车——建库零代码风险，外加一段不碰执行链路的端点代码）

### 验收口径

- 三角色各登录一遍：member 看不到任何 admin/operator 菜单与数据（含 API 直打 403/404）；operator 能处理适配与别名/默认值，但打开他人 private 场景详情得 404、翻他人执行明细得 404；admin 用户管理可用、能看到全员私有场景。
- 执行完成/适配应用后，接收人铃铛出现未读且深链可达。
- 删除一个测试用户走完三种处置，执行记录仍在且显示「已注销」。
