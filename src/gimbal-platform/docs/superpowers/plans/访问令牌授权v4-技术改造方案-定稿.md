## 0. 结论

v3 把入站调用方登记成一个外部系统别名，再用 `gic_`（调用方）+ `ggt_`（被代表用户）两枚令牌认证。别名本是右侧被调系统的抽象，拿它表达左侧调用方造成了一串错位：承载别名、`is_carrier`、调用方白名单、少带一个头即降级为平台模式、转让时别名变共享等。

v4 按三段收敛：

```
左侧                         中间                          右侧
用户本人 / 持有令牌的第三方 ──▶ Gimbal（以该用户身份执行）──▶ 编排的场景（多系统串行）
授权：用户签发的访问令牌        权限：与该用户 JWT 登录相同        目标：服务别名 + 凭证池
```

- **左侧只有一种令牌 `gtk_`**，绑定一个用户（个人令牌）或平台系统用户（平台令牌）。调用方不在 Gimbal 登记。
- **令牌下管理授权范围**：允许使用的服务别名与凭证。调用、注册、每次定时运行前，由平台计算本次用到的别名与凭证并核对。
- **约束先松、追溯先行**：直连地址与场景内置凭证不拦截，完整记录并打标记；收紧时把标记改为拒绝即可。
- **个人设置**改为锚点分区（账号 / 访问令牌 / 工作台身份卡 / 通知）；工作台身份卡可自定义；便签做成独立的工作台注册卡。

不新增模块。平台未上线，v3 入站存储直接替换，不做兼容层。

## 3. 判定链

### 3.1 入站即时请求

```
① 认证：hash 命中 → 未吊销、未失效、未过期 → 属主角色 member+ 且 `is_active`（平台令牌跳过角色；`is_active` 为兜底——停用正常路径已在停用时落库 `invalidated(deactivated)` 由「未失效」先行命中，兜底命中同样返回 401 `token_invalidated`）
② M1：请求不带配方，含 graph（既有，runs.py:73-79）
③ 方案物化（既有）
④ 身份范围：个人 can_run_scenario；平台 = 公共场景 + 只读闸 + 非 graph / 非临时调用
⑤ 令牌范围：别名集 ⊆ scope.aliases ∧ 凭证集 ⊆ scope.auths → 否则 403 resource_not_allowed{aliases, auths}
⑥ 追溯计算：解析目标（含来源层）、内置认证名单、范围外标记
⑦ 派发 → 回调（令牌回调）→ 审计
```

④ 先于 ⑤：先回答「能不能跑这个场景」，再回答「这次碰到的资源是否被授权」，错误信息更好理解。

### 3.2 集合计算（单一实现，执行、注册、预检、定时复核共用）

| 集合 | 场景执行 | 临时调用 |
|---|---|---|
| 别名集 | `referenced_services(steps)` 中经第 ③ 层（别名 base_url）或绑定指向别名解析的服务键 | `steps[].service`（本就是别名名，`adhoc_run.py:155`） |
| 凭证集 | `exec_auth_aliases`（模板扫描 ∪ 绑定 authAlias ∪ 别名默认凭证，`service_aliases.py:301`；**模板扫描源含 `config.setup/teardown` 条目 `params` 中的 `${auth.*}`**，D30）∪ 注入条目物化 | 同用 `exec_auth_aliases(steps)`，退化为步骤模板扫描 ∪ 别名默认凭证（body 中的 `${auth.*}` 一并算入） |
| 范围外标记（不拦截） | 走第 ①（方案绑定 url）或 ②（场景 authored）层的服务；场景 `config.users` 内置认证；`config.setup/teardown` 中越白名单的策略条目（`strategyEntries`，D30） | 无 |

服务地址三层解析的唯一组装点仍是 `run_materialize.service_url_resolved` / `_apply_services`（`run_materialize.py:111`），新增一个只读函数返回每个服务的 `{url, source, alias?}`，不另写第二份优先级链。

graph 不在本表：令牌路径在 ② 已整体拒绝（D20），不会出现「顶层无 steps → 集合为空 → 任何范围都通过」的旁路。日后若向令牌开放 graph，集合计算直接复用 `graph_dispatch._all_referenced_services`（`graph_dispatch.py:335`）与 `run_prepare.graph_auth_aliases`（`run_prepare.py:400`），并补只读闸的多单元覆盖。

### 3.3 定时任务每次运行前复核顺序

在 `integration_runner` 现有前置检查处（约 893–946 行）替换 `inbound_disabled` / `grant_revoked` / `scope_denied` 三段。

**作用域条件（必须照搬，否则会误停）**：

- **#1–#4、#6 只作用于注册方自己的实例**：`tpl.token_id IS NOT NULL ∧ inst.holder_id == tpl.owner_id`（个人令牌），或平台令牌模板的唯一平台实例。这与现有 grant 复核的条件一致（`integration_runner.py:917-919`）。
- **订阅者实例**按自身 JWT 身份与凭证池运行（`integration_runner.py:993`），由订阅者自己管理，不受注册令牌的吊销、到期、范围影响。
- **#5 只作用于经平台令牌注册的平台任务**：`tpl.identity_mode == "platform" ∧ tpl.token_id IS NOT NULL`。JWT 创建的平台任务（集成页入口，D22）不绑令牌，沿用 v3 豁免（`integration_runner.py:934` 的 `caller_alias_name` 条件改写为 `token_id`），只读闸照旧。

| 序 | 检查 | 失败暂停原因 | 恢复 |
|---|---|---|---|
| 1 | 令牌已吊销 | `token_revoked` | 「迁移任务」到另一张令牌后自动解除（§3.4）；或 JWT 管理者「解绑令牌」（§5.3，D26/D28）后在集成详情「启动」 |
| 2 | 令牌失效（改密 / 停用）；**或属主 `is_active = false`（兜底，与认证路径 §3.1① 成对——防未来新增停用入口漏置失效：即时请求被 ① 拦下，定时任务在此拦下，不留「停用账户的令牌任务照常跑」的半边兜底）** | `token_invalidated` | 重新生成后**自动恢复**（属主恢复 + 重新生成） |
| 3 | 令牌自然到期 | `token_expired` | 续期或重新生成后**自动恢复** |
| 4 | 属主角色 < member（停用不在此列：停用即落库失效，走 #2 `token_invalidated`，重新启用也不恢复） | `token_owner_ineligible` | 恢复角色后由持有人在集成详情「启动」 |
| 5 | 平台令牌：场景非公共 | `scope_denied`（沿用）；判定只认公共（D7），替换 v3 `platform_scope_ok` 的别名属主分支（D28 同源，M2） | 同既有 |
| 6 | 令牌范围不满足 | `resource_not_allowed` | 放宽范围后「启动」 |

暂停均发 `integration.paused` 回调与站内通知：个人令牌通知属主（点对点，沿用 `inst.holder_id` 路径）；平台令牌通知 member+，复用现有扇出分支（`integration_runner.py:1300-1316`），只新增 `token_*` 原因的标题与正文。

**现存缺陷，随 P1 修**：扇出分支与 `integration_runner.py:1631` 共 3 处按 `User.role.in_(("admin", "operator"))` 选收件人（`:1304`、`:1314`、`:1631`），`operator` 已在 09-29 三级更名中改为 `member`，因此平台任务的暂停与告警通知目前只发给 admin、member 一直收不到。改为 `("admin", "member")`，并补一条按角色扇出的单测。另外 `integration_runner.py:753-760` 的「模板变更需重新确认」通知是点对点发 `inst.holder_id`，对平台实例会发给系统用户（无人可见），一并改走同一扇出。自动恢复走现有复活钩子 `revive_paused_instances` 的同一机制（凭证补齐即恢复的那套），扩展为识别 `token_*` 暂停原因。

### 3.4 令牌轮换与任务迁移

v3 有意让「吊销单个 `gic_` 不影响已注册任务」（`integration_runner.py:895-898`），否则先发新、再吊旧的轮换会停掉调用方的全部任务。v4 吊销为终态，因此提供两条轮换路径：

| 路径 | 步骤 | 适用 |
|---|---|---|
| 原地重新生成 | 「重新生成」→ 调用方换新明文 | 能接受调用方切换期间的短暂 401；任务绑定的令牌 id 不变，无需迁移 |
| 新旧并行 | 建新令牌 → 调用方切到新令牌 → 「迁移任务」（旧 → 新）→ 吊销旧令牌 | 需要零中断切换 |

迁移任务（`POST /api/me/access-tokens/{id}/migrate-tasks`，`{toTokenId, taskIds?}`，缺省为全部；`toTokenId != id`）：

- 两张令牌必须同一属主、同一 kind；目标令牌须为**有效状态且属主满足角色条件**（member+；否则迁过去每请求都 401，等于没迁，M6）。
- 逐个任务用目标令牌范围做预检（§3.2 同一实现），不满足的列入响应的 `skipped` 并说明缺少项，满足的改绑 `token_id`。
- 已改绑任务的 `token_*` 类暂停原因一并清除并重新排期，记 `integration.resumed` 时间线与 `token.tasks.migrate` 审计。
- **回调目标随令牌变化**：任务的回调 = 令牌 `callback_url` + 任务自身的 `callback_path_override`，改绑后事件（含紧接着的 `integration.resumed`、之后的 `run_finished` / `paused`）发往**新令牌**的地址、用新令牌的签名密钥。调用方若没改监听，事件会静默丢失。因此迁移响应逐任务带 `callback: {from, to, changed}`，`changed=true` 时前端醒目提示「回调地址 A → B，签名密钥已变更，请确认调用方已切换监听」；新令牌未配置回调时提示「迁移后该任务不再回调，只能轮询」。
- 吊销对话框里若该令牌仍有注册任务，提示「先迁移到…」，给出一键迁移入口，并在确认前展示同样的回调变化。

平台令牌同形：`/api/integration/platform-tokens/{id}/migrate-tasks`（member+）。

### 3.5 令牌生命周期状态机（实现与测试对齐用）

```
                ┌──────────────────────────── re-create（同属主新令牌，新 id） ──┐
                ▼                                                            │
 创建 ──▶ 有效 ──续期──▶ 有效(新到期)                                         │
          │  │  \──自然到期──▶ 已到期 ──续期/重新生成──▶ 有效                  │
          │  \──改密/停用──▶ 已失效 ──重新生成──▶ 有效                         │
          \────吊销──────────▶ 已吊销（终态；任务迁移走 §3.4，或解绑走 D26）────┘
 派生态（不落库，认证时计算）：属主角色 < member → 拒绝 403 token_owner_ineligible
（属主停用不是派生态：停用时已落库 invalidated(deactivated)，认证走 401 token_invalidated）
```

| 操作 | 前置状态 | 效果 | 对任务 |
|---|---|---|---|
| renew | 有效 / 已到期 | 请求体 `{ttlDays}`，新到期 = **now + ttlDays**（不在原到期上叠加，D29 上限自然成立） | 到期暂停的自动恢复 |
| regenerate | 非吊销均可 | 新 hash/hint、清失效、重设有效期 | 失效/到期暂停的自动恢复 |
| revoke | 非吊销均可 | 终态 | `token_revoked` 暂停（仅注册方实例，D19） |
| unbind（任务侧，D26） | 任务任一状态 | `token_id` 置空、停回调、清 `token_*` 暂停但保持 paused 待「启动」；平台任务先过 D28 预检 | 转 JWT 管理 |
| migrate（§3.4） | 源任一状态（含吊销）、目标有效 | 改绑 + 范围预检 + 解暂停 + 回调变化回报 | — |

### 3.6 已知边界

- 范围在**请求时**核对；已入队、尚未被 worker 领取的执行不再复核（与 v3 grant 现状一致）。窗口为排队时长。
- JWT 执行不受令牌范围约束。
- 直连 URL 与内置认证只记录不拦截（D15）。
- `POST /api/runs` 无幂等键：调用方网络层重试会产生重复执行（v3 同）；`clientRef` 供事后对账。幂等键本期不做（§13）。
- D28 只在解绑入口拦一次：解绑后场景转私有不再被拦（任务已成 D22 豁免类），与 v3 JWT 平台任务的暴露面同款；要彻底关闭需把 #5 扩到全部平台任务，属行为变更，本期不做。

## 4. 数据模型（alembic `0033_access_tokens`）

### 4.1 新表

```sql
access_tokens
  id               bigserial PK
  user_id          int  FK users(id) ON DELETE CASCADE   -- 个人 = 属主；平台 = __platform__
  kind             varchar(16)                  -- personal | platform
  name             varchar(64)
  token_hash       char(64) UNIQUE              -- sha256(gtk_…)
  token_hint       varchar(16)                  -- 'ab12…9f3c'，仅展示
  expires_at       timestamptz
  invalidated_at   timestamptz NULL
  invalidated_reason varchar(16) NULL           -- password | deactivated
  revoked_at       timestamptz NULL
  last_used_at     timestamptz NULL             -- 1 分钟节流写
  callback_url     varchar(512) NULL
  callback_secret  text NULL                    -- Fernet，签名用
  callback_key_alerted_at timestamptz NULL  -- 首次 signing_key_missing 通知时刻(去重);rotate 清空
  created_by       int NULL FK users(id) ON DELETE SET NULL  -- 平台令牌的签发人；签发人删号不阻塞
  created_at / updated_at
  INDEX (user_id, revoked_at)

access_token_scopes
  id          bigserial PK
  token_id    bigint FK access_tokens(id) ON DELETE CASCADE
  alias_name  varchar(128) NULL FK service_aliases(alias_name) ON DELETE CASCADE ON UPDATE CASCADE
  auth_id     int NULL FK auth_sessions(id) ON DELETE CASCADE
  CHECK ((alias_name IS NULL) <> (auth_id IS NULL))
  UNIQUE (token_id, alias_name), UNIQUE (token_id, auth_id)
```

- 范围按对象外键存：别名或凭证删除后授权随之消失，同名重建不会自动继承授权；别名改名级联。
- 删除用户时端点先显式删除其个人令牌（便于审计）；`user_id` 的 CASCADE 是兜底，`executions.token_id` 等引用随之 SET NULL，追溯靠快照（§7.1）。
- 凭证按 `auth_sessions.id` 存，核对时把执行注入的凭证别名映射为属主池里的 id。
- 令牌片段需要单独存 `token_hint`，因为库里只有哈希。
- 投递的 URL 与 `token_name` 在建行时快照（既有 `_add_delivery` 形状），令牌删除后行不丢；**但签名密钥不快照**——现实现按调用方现取（`webhook_outbox.py:340-353` `_load_secrets`），且取不到时跳过签名头照常发送（`:271-275` `if secret:`）。v4 修正见 §6「投递必须带签名」：密钥取不到 → `failed(token_deleted / signing_key_missing)`（按因分码），绝不裸发。

## 5. 接口

### 5.1 个人令牌（JWT only）

| 端点 | 行为 |
|---|---|
| `GET /api/me/access-tokens` | 列表：元数据 + 派生状态 + 范围计数 + 已注册任务数（含不满足数）。派生状态含「范围已清空」：别名或凭证被删除级联后两个维度之一为空时显示，提示「所有调用都会被拒，请编辑范围」，避免用户只看到全部 403；含「签名密钥不可用」：回调密钥解密失败（FERNET_KEY 轮换后）时显示，提示「请轮换签名密钥」，见 §6 |
| `GET /api/me/access-tokens/scope-candidates` | 全部服务别名 + 本人凭证池 |
| `POST /api/me/access-tokens` | `{name, ttlDays(≤365, 缺省 90), callbackUrl?, scope:{aliases, authIds}}`；member+；上限 5（事务内锁 users 行计数）；范围非空；回调主机白名单；返回一次性 `{token, callbackSecret?}` |
| `GET /api/me/access-tokens/{id}` | 详情：范围、回调、已注册任务（逐个预检结果）、最近调用（含被拒） |
| `PUT /api/me/access-tokens/{id}/scope` | 整体替换；响应附「受影响任务」；前端在收紧时先 `?dryRun=1` 取影响面再确认 |
| `POST /api/me/access-tokens/{id}/renew` | 仅「有效 / 自然到期」；请求体 `{ttlDays}`，新到期 = now + ttlDays（不叠加，M3）；改密或停用失效 → 409 `regenerate_required`；到期时点 ≤ 上限（D29） |
| `POST /api/me/access-tokens/{id}/regenerate` | 非吊销均可；新明文、新 hint、清失效、重设有效期；触发任务自动恢复 |
| `POST /api/me/access-tokens/{id}/callback-secret/rotate` | 新密钥一次性返回 |
| `PUT /api/me/access-tokens/{id}/callback` | 改地址（白名单）。**设置地址时若签名密钥为空，自动生成一个并随本响应一次性返回明文**（照搬 v3 首开即发的口径，`routers/service_aliases.py:468`——否则「先建令牌、后配回调」这条常见路径下每条投递都会 `signing_key_missing` 失败）；前端复用 TokenSecretDialog 展示。**清空回调地址时保留密钥**——以后重新设置地址不会悄悄换掉密钥，接收方验签不中断；要换密钥显式走 rotate |
| `POST /api/me/access-tokens/{id}/migrate-tasks` | `{toTokenId(!=id), taskIds?}`：改绑到同属主另一张有效令牌，逐个范围预检，返回 `{migrated[{taskId, callback:{from, to, changed}}], skipped[{taskId, notAllowed}]}`；支持 `?dryRun=1` 先看影响与回调变化；清除 `token_*` 暂停并重新排期（§3.4） |
| `DELETE /api/me/access-tokens/{id}` | 吊销（软，保留行供审计）；有注册任务时响应带 `pendingTasks`，前端提示先迁移 |

user 角色（M6 补全）：**仅列表只读 + 吊销**；创建、续期、重新生成、改范围、迁移任务、改回调地址、轮换签名密钥一律 403 `role_forbidden`。

**已吊销令牌锁定只读**（吊销后仍有在途事件要投递，§6——回调地址若还能改，等于能把它们转发到任意白名单内地址）：仅允许查看、删除响应的 `pendingTasks` 提示、以及作为 `migrate-tasks` 的**源**；`PUT scope`、`PUT callback`、`callback-secret/rotate`、`renew`、`regenerate` 对已吊销令牌一律 409 `token_revoked`（后两者的前置状态已天然排除，此处写死成口径）。平台令牌同款。

### 5.2 平台令牌（JWT，member+）

### 5.4 错误码

新增：`token_invalid`(401)、`token_expired`(401)、`token_invalidated`(401)、`token_owner_ineligible`(403)、`resource_not_allowed`(403/422)、`regenerate_required`(409)、`token_limit_reached`(409)、`token_revoked`(409，吊销令牌上的写操作)、`scope_empty`(422)、`callback_host_not_allowed`(422)。

**认证错误的映射口径（M7）**：令牌**不存在**与**已吊销**统一返回 401 `token_invalid`，不区分——避免调用方拿响应差异探测令牌是否存在（吊销与否属主在 UI 可见，无需向调用方区分）；**过期** 401 `token_expired`、**失效**（改密/停用）401 `token_invalidated` 单列，持有人排查时一眼可辨。

删除：`inbound_disabled`、`grant_*`、`grant_header_on_jwt`、`identity_mode_mismatch`（模式由令牌决定，请求不再声明）。

## 6. 回调

- URL = 令牌 `callback_url` + 可选 `callbackPath` 覆盖（沿用 `valid_callback_path` 只接路径段）。
- 主机白名单：一期为部署配置 `CALLBACK_HOST_ALLOWLIST`（逗号分隔，支持 `*.internal` 后缀匹配），保存时校验主机名。**缺省空列表 = 任何回调地址都不允许保存**——部署不开回调能力时无需配置，令牌仍可全功能轮询使用；要开回调必须显式配置。
- **白名单是唯一的内网防线**。被测和集成系统都在内网，RFC1918 网段不能整体拒绝，所以白名单要按「具体回调主机」配置，不要配成宽泛的通配。
- 投递时防 DNS rebinding：对主机**只解析一次**，校验解析出的 IP 不在 loopback、link-local（含 `169.254.0.0/16`）、`0.0.0.0`、`::1` 之内，然后**直接连接这个 IP**（Host 头与 TLS SNI 仍用原主机名）。不允许 HTTP 客户端在连接时再次解析，避免「校验时一个 IP、连接时另一个 IP」。
- 签名密钥沿用现有 Fernet 设施（`webhook_outbox` 已在用 `fernet_decrypt`）。

**投递必须带签名（H1，11-04 第四轮定案）**：密钥在投递时按令牌现取（不快照进投递行）。现实现取不到密钥（令牌已删/解密失败）会跳过签名头照常发送——安全性退化：接收方不强制验签就会接受一条无法证明来源的事件。v4 改为：

- 取不到密钥 → 该投递行置失败，**绝不以无签名方式发送**；手动补发走同一检查。**原因码分两种**：令牌行不存在（用户删除）→ `token_deleted`（§5.3 显式置位同码，不触发密钥通知）；行存在但密钥为空/Fernet 解密失败 → `signing_key_missing`。现实现「解密失败仅 warning 后裸发」（`_load_secrets` 内）一并改掉。
- 删除用户时（§5.3）：令牌行随 CASCADE 删除前，其名下 `pending` 投递**显式置为 `failed(token_deleted)`**，不留无签名发送的窗口。
- **吊销不是删除**：吊销为软终态、行保留、密钥保留——吊销前已在途的事件、以及触发 `token_revoked` 暂停的 `integration.paused` 事件，照常**带签名**投递（调用方靠它感知吊销并轮换）。
- **FERNET_KEY 轮换的静默失败面（建议补，11-04 第五轮）**：H1 之后密钥解密失败从「裸发退化」变为 `failed(signing_key_missing)`——安全上正确，但轮换 `FERNET_KEY` 会让**全部令牌**的回调一起失败，且无人知晓。处置：(a) 令牌列表派生状态「签名密钥不可用，请轮换」（解密失败触发，§5.1）；(b) 每张令牌**首次**出现 `signing_key_missing` 时给属主发站内通知（平台令牌通知 member+，走 §3.3 扇出分支），同令牌去重不刷屏——去重标记 = `access_tokens.callback_key_alerted_at`（§4.1），`callback-secret/rotate` 时清空，之后再恶化还能再报；(c) §11 面向运维的提示。恢复路径就是既有的 `callback-secret/rotate`（新密钥用新 FERNET_KEY 加密，立即恢复投递）。

**钉 IP 的实现注记（不是配置项，按开发项估）**：投递用的是 `httpx.AsyncClient`（`webhook_outbox.py:408`，`follow_redirects=False` 保持不变——重定向不跟随，第二跳 SSRF 已封），它没有「连接用 IP、Host 与 SNI 用域名」的现成参数。

- HTTP 回调：URL 主机替换为钉住的 IP，显式设置 `Host` 头即可。
- HTTPS 回调：URL 不能改成 IP（证书校验与 SNI 都依赖主机名）。做法是给 `AsyncHTTPTransport` 换一个自定义的 httpcore 网络后端，覆盖 `connect_tcp`：按「主机名 → 已校验 IP」的映射直接连 IP，URL 保持原主机名，TLS 的 `server_hostname` 与 `Host` 自然正确，也不会触发二次解析。
- 解析与校验放在投递循环每行开始时做一次，映射只在本次请求内有效。
- 单测覆盖 HTTP、HTTPS 两条路径，以及「解析到 loopback / link-local 被拒」与「连接时不发生第二次解析」。
- 签名、重试、`X-Gimbal-Delivery` 去重、手动补发不变；补发权限 = 令牌属主或 admin（平台令牌 = member+）。
- payload：`caller` 字段由别名改为 `{tokenId, tokenName}`。
- 公共模板只给注册令牌回调（沿用 v3 集成指南「公共模板仅注册方实例写回调投递行」口径——非本文 D12，D12 是改密决策）。

## 11. 风险

1. **范围外目标只记录不拦截**：令牌范围对直连地址与内置认证无约束，安全性依赖审计。收紧路径已预留：把 `outOfScope` 非空从标记改为拒绝。
2. **排队窗口**：请求时核对，排队中改范围不影响已入队执行。
3. **平台令牌长期有效**：365 天上限（D29 个人同）需续期；签发人离职不影响（属于平台），审计记签发人。
4. **一张令牌给多个第三方**：审计无法区分，靠「一个调用方一张令牌」约定。
5. **便签多设备并发**：整值覆盖，后写为准。
6. **无幂等键**：调用方网络重试产生重复执行（v3 同），`clientRef` 对账兜底；上线后按调用方反馈决定是否做幂等键。
7. **暴力探测的审计噪声**：认证失败逐条入审计（不记明文，只记 hint/前缀），无速率限制（§13）；上线后观察审计量再决定采样或限频。
8. **FERNET_KEY 轮换是全量回调停摆事件**：轮换后所有令牌的签名密钥不可解密，投递逐条 `signing_key_missing` 失败（§6）。运维手册必须写明：**轮换 FERNET_KEY 后需通知全部令牌属主轮换签名密钥**（平台侧有派生态 + 站内通知兜底，但不能只依赖它）；属主 rotate 后立即恢复。
