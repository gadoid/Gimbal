# 服务注册与拓扑管理平台 — UI/UX 架构与交互设计方案

## 1. 项目背景与设计目标

### 1.1 背景概述
平台核心定位为**跨系统接入与微服务运行时拓扑配置中心**。上游接入通用接口定义（如 Plate 组件库定义的 API/Schema，不携带环境与运行时元数据），下游承载实际物理/容器端点的映射与访问凭据管控。旧版页面存在层级结构模糊（仅单层列表折叠）、缺乏清晰的拓扑关系表达、配置操作分散等体验痛点。

### 1.2 核心业务与拓扑模型（3 层结构）
1. **第一层：服务（Service）**
   - 与上游（Plate / OpenAPI / 第三方接入）的接口定义契约强绑定。一个服务代表一套标准化的接口定义。
   - 关注属性：契约版本（Schema Hash）、协议类型（gRPC / HTTP / OIDC）、归属链路、变更动态感知。
2. **第二层：实例（Instance）**
   - 部署在具体物理机、K8s 集群或容器网关的具体节点。从属于某个服务，是真实运行时的网络端点（Base URL）。
   - 关注属性：部署环境与业务 Tag（dev/test/staging/prod/IDC）、连通性探针状态、延迟、流量权重。
3. **第三层：服务配置管理 / 凭据别名（Credential Slots & Aliases）**
   - 细粒度权限管控与调用上下文配置。挂载于具体实例之下，针对不同调用方或使用场景（如只读审计、主流程扣款、压测模拟）派生不同别名。
   - 关注属性：身份凭据（API Key / Token / mTLS 证书）、默认注入请求头（Default Headers）、注入参数（Params）、鉴权探针与连通性验证。

## 2. 交互逻辑与信息架构设计

### 2.1 整体用户动线（User Journey）
```mermaid
graph TD
    A[服务注册与拓扑管理 主页概览] -->|感知上游变化| B[Plate 差异感知与接口批量映射]
    A -->|点击服务卡片| C[服务展开与实例分页态]
    C -->|实例筛选/动态打标| D[Creatable Tag 分组联动]
    C -->|点击具体实例的 服务配置管理| E[侧滑抽屉: 服务配置管理]
    E -->|维护多凭据别名| F[默认凭据 / 审计凭据 / 鉴权测试]
```

### 2.2 核心交互亮点

#### ① 优雅就地展开与高密度实例分页（避免视觉塌陷）
- **设计决策**：摒弃多层手风琴无线深层嵌套。主列表采用服务卡片流，点击“展开实例列表”在卡片内部高保真平铺展开。
- **分页机制**：当挂载实例超过 5 个（如 8 个）时，自动激活紧凑型分页控件（每页 5 条 / 支持翻页与快捷切换），保证单屏信息密度与可阅读性。

#### ② 动态 Tag 收集与自适应分组（Creatable Tag Select）
- **痛点解决**：Plate 上游不带环境与业务元数据，纯手写导致脏标签（如 test、TEST、测试），纯后台字典又导致接入被阻断。
- **解决方案**：
  - 输入框默认提供系统已存在的环境 Tag（dev/test/staging/prod）与活跃业务分组；
  - 支持就地输入新标签并回车快速创建，新 Tag 自动全局收录到顶部筛选器中；当实例全部移除时自动清理。

#### ③ 抽屉式侧边栏配置管理（Drawer Modal）
- **更名规范**：统一将原“实例凭据与别名”命名为 **「服务配置管理」**。
- **抽屉承载**：点击实例条目的“服务配置管理”后从右侧滑出抽屉，不丢失主页面上下文。抽屉内分块展示“网络端点健康指标”与“多凭据别名及默认注入参数配置”，支持单槽位独立快速连通性测试。

## 4. 前端组件与技术落地规范
- **设计规范系统**：基于 Geist 字体体系，以 Mesh Blue (`#2563eb`) 为交互主强调色，表面中性底色 (`#f8f9ff` ~ `#eff4ff`)。
- **状态流转响应**：网络探针 HTTP 200 (绿色)、待接入待配置 (琥珀黄)、网络熔断/502 (告警红)。
- **持久化建议**：Tag 字典维护在前端缓存及后端租户级元数据库，随实例生命周期动态增减。
