## 0. 为什么要重新设计

原模型：release_id 按时间编号（`YYYY.MM.N`），每个系统一条线性序列，冻结只收已评审块。它回答的是「plate 在某个时间点的定义快照」。

用例关心的却是「被测系统某个版本的接口是什么样」。两者的错位导致了一串问题：

| 问题 | 根源 |
|---|---|
| 测试阶段没有固定版本可用，只能用 working，而 working 一直在变，适配时找不到起点 | 只有一种发版，且只收已评审内容 |
| 为此放开「冻结未评审内容」后，只要树里有草稿，就再也没有「全部已评审」的版本，`latest` 停滞 | 一个时间序列同时承担「描述新版本」与「修正已有定义」 |
| 每次发版都被当作「一个新版本」提示用户升级，大部分其实只是定义修正 | 同上 |
| 无法判断场景的版本与环境部署的版本是否一致 | release 不知道自己对应被测系统哪个版本 |
| 生产与测试并行时，无法修补旧版本的定义 | 只有一条线 |

这些问题打补丁（加发版类型、加提示规则）都只能缓解。本文改为让版本模型直接对应被测系统的版本。

## 1. 概念

| 概念 | 定义 | 示例 |
|---|---|---|
| 系统 | plate 中的一个被测系统 | `fin` |
| **版本线（line）** | 被测系统的一个版本。版本线之间的差异 = 被测系统本身的变化 | `fin@3.2` |
| **修订（revision）** | 版本线内的不可变快照。同一版本线的各修订描述同一个被测系统版本，差异只是 plate 描述的变化：补充、更正、评审完成 | `fin@3.2#4` |
| **已验证修订** | 场景最近一次通过保存检查时所依据的修订，记在 `meta.plate` 中 | `{"fin": "3.2#4"}` |
| **生效修订** | 一次执行实际使用的修订，由已验证修订推出（4.2） | `3.2#6` |
| working | main 分支的当前树；只用于 plate 编写者查看效果（第 6 节） | — |

## 2. 版本线

### 2.1 声明在源树中

版本线写在系统入口文件 `systems/<系统>/system.md` 的 frontmatter 里：

```yaml
---
type: system
system: fin
line: "3.2"
predecessor_line: "3.1"   # 首条版本线可省略
line_scheme: semver       # 2.4（L1 已定）；缺省 free
line_source: manual       # 2.4；缺省 manual（另可选 service_version）
---
```

- 发版时版本线从源树读出，不由命令行参数指定。
- 进入下一条版本线 = 修改这两个字段，本身是一次需要评审的变更。
- `line`、`predecessor_line` 及 2.4 的 `line_scheme` / `line_source`（pattern 口子另加 `line_pattern`）都是知识侧 Frontmatter 的加法字段（P8）。

### 2.2 与 git 的关系

- **main 对应最新的版本线**，即正在开发的被测系统版本。
- **旧版本线的维护在分支上进行**。约定：main 上合入第一个属于下一条版本线的变更（即修改 `line` 的那次变更）之前，先从当前提交拉出该版本线的维护分支，例如 `plate/fin/3.2`。
- 同一个修正如果几条版本线都需要，用 cherry-pick 同步。内容寻址保证同样的对象在各条线上共享存储。
- 一个维护分支只服务一个系统的一条版本线。common 层和 git 分支都是整个仓库共用的，所以在 fin 的维护分支上不得为其他系统发版；第 3.3 节的祖先校验会拦下这种情况。

### 2.3 顺序与生命周期

- **顺序**由 `predecessor_line` 串成链，不依赖版本号的字面排序（被测系统的版本号不一定是 semver）。
- **开启**：随 2.1 的字段变更自然发生；该版本线的第一个修订发出后即可被场景使用。
- **退役**：没有任何环境声明某条版本线时，视为退役（第 5 节）。退役只影响提示与冷化判定，不影响已声明它的场景执行。

### 2.4 版本线标识的方案与来源（L1，已定）

版本线标识**多模式、可配置**。配置写在 `systems/<系统>/system.md` 的 frontmatter，走「编写 → 评审 → 入库」主线，由 plate 校验：

| 项 | 决定 |
|---|---|
| 格式 `line_scheme` | 内置 `semver` / `iteration` / `date` / `free`，另加 `pattern`（配合 `line_pattern` 正则）作为自定义口子；缺省 `free` |
| 来源 `line_source` | 只允许来自源树：`manual`（frontmatter 的 `line` 字段，缺省）或 `service_version`（取 `gimbal:system` 中指定服务的 `version`）；不支持从 git tag 或外部系统取 |
| 作用范围 | scheme 只影响校验和展示；版本顺序始终由 `predecessor_line` 链决定，模型语义与格式无关 |
| 单线模式 | 天然支持（持续部署、没有版本的被测系统取 `free` 单线）：所有结构变化表现为线内修正，安全性不变，只是失去「多个版本并存」的能力 |
| 平台侧 | 只读：`GET /api/system/{id}/lines` 返回版本线时带上 `line_scheme`；环境组里的版本线只能从 plate 已有的版本线中选择，平台不做 scheme 校验 |
| 图形化配置 | 暂不做，随 plate 写入能力（plate-design 8.1 延后项）一并设计。**约束：任何经由界面的写入，都必须产生一次进入评审的变更，不得直接修改 plate 的运行状态**——保证版本线变更可评审、修订沿 git 祖先关系前进、主线流程不被绕开 |

fin / platform 的具体 scheme 选择不阻塞 RS0：RS0 先按 `free + manual` 实现，具体配置在 RS3 前结合两个系统的实际发布节奏确定。

## 3. 修订

### 3.1 冻结范围

每个修订冻结系统树中**通过机械校验的全部块**，逐对象记录评审状态。不再区分「正式版 / 测试版」：成熟度由评审状态计算得出，不由签发人选择。

冻结范围写明（已定，D-3）：`gimbal:system`（服务声明）**随修订冻结**——服务声明是接口坐标的一部分；`gimbal:defaults` **不冻结**——它是新建场景的起点配置（偏环境属性），平台读 working（Release 方案 6.1）。

### 3.2 发布闸门

原有四项检查保留，阻塞范围按评审状态区分：

| 检查 | 已评审对象 | 草稿对象 |
|---|---|---|
| 方言错误（F0） | 阻塞（文件无法解析就无法冻结，不分评审状态） | 阻塞 |
| 机械检查（F / T / S 阻塞级、F2） | 阻塞 | 降为告警，写入 manifest 的 `warnings` |
| C 类一致性 | 阻塞 | 降为告警 |
| 引用闭包 | **已评审对象只能引用已评审对象**（块与词条） | 草稿之间可以互相引用 |
| F4 交付件清单阈值 | 按已评审对象计算 | 不计入 |
| 人签发 | 必须 | — |

现状对照：现在闸门对整棵树运行 `validate_system_tree`，任何阻塞级 finding 都拒绝发版（`release.py` 修订十一「零 finding 才能发版」）。草稿进入修订后，按现状规则，一个写到一半的草稿就会挡住整条版本线的发版。

分级规则（已定，D-4）：

- **树级与唯一性检查不论评审状态一律阻塞**（与 F0 同级）：F3 的接口 id、路由键、片段 id、交付物 id 重复——草稿也进修订，manifest 按 id 索引，重复即歧义。
- 其余能定位到对象的 finding：**涉及任一已评审对象即阻塞**；只涉及草稿对象则降为告警（写入 `warnings`）。
- 实现前提：解析器目前只记块起始行，Finding 只有 `source` / `line`——**RS0 第一项**为 Block 补**结束行**，使 finding 能按行号区间映射到块与对象。

### 3.3 修订必须沿 git 祖先关系前进

- manifest 记录来源 commit（`source_commit`）。
- 发第 N+1 个修订时，`source_commit` 必须是第 N 个修订 `source_commit` 的后代（`git merge-base --is-ancestor`），否则拒绝。
- 版本线的第一个修订不做此检查，但源树中的 `line` 必须是一条尚无修订的新版本线，且 `predecessor_line` 必须已发出至少一个修订（首条版本线除外）。

这条规则同时防止：在 main 上为旧版本线发修订（main 已包含下一条线的变更，不是旧线最近修订的后代）、在别的系统的维护分支上发版、重写历史后再发版。

### 3.4 编号

修订号为 `<line>#<n>`，n 在版本线内从 1 递增。与 git 祖先校验一起，保证同一版本线的修订是一条全序。

### 3.5 manifest

| 字段 | 内容 |
|---|---|
| `system`、`line`、`revision` | 定位 |
| `predecessor_line` | 版本线顺序 |
| `previous_revision` | 线内上一个修订 |
| `source_commit` | 3.3 的祖先校验与溯源 |
| `objects[]` | `{id, type, hash, review, shape_hash}`；`shape_hash` 仅 endpoint |
| `call_projections` | `{endpoint_id: <投影对象 hash>}`，投影入对象池 |
| `corrections` | 与线内上一个修订相比，`shape_hash` 发生变化的接口列表（只列在两个修订中都存在的接口） |
| `warnings` | 草稿对象上的 finding（3.2） |
| `sut_version` | 可选，被测系统的版本标识，用于展示（与 `line` 相同时可省略） |
| `m2_version` | 知识侧模型代际，**水合门** |
| `m2_hash` / `m2_generation` | 冻结时的用例侧 M2，只作溯源 |
| `dialect_version`、`signed_by`、`signed_at`、摘要 | 沿用 |

对象文件统一为信封 `{"type": ..., "data": ...}`。不再读取旧格式：至今没有任何正式发版（`plate_artifacts/` 被 `.gitignore` 排除，只有演练时的临时冻结），第一个正式修订直接使用本格式。

### 3.6 发版入口

发版只通过 CLI 在 git 工作树中执行（`plate release <系统>`），因为 3.3 需要 git。现有的 HTTP 发版动作（`routes_grammar.py::action_system_release`）删除：它是一项写操作，与 S1「plate 不提供 HTTP 写入」的已定原则不符，也无法做祖先校验。

## 4. 场景侧的版本声明

### 4.1 `meta.plate`

`meta.plate: {系统: "<line>#<n>" | "working"}`，例如 `{"fin": "3.2#4", "platform": "1.5#2"}`。值是**已验证修订**：场景最近一次通过校验时依据的修订。只有以下操作会改变它：

- 新建、复制：取所选修订；
- 普通保存：编排页按**生效修订**加载定义（4.2），保存时校验通过后，已验证修订更新为当时的生效修订。两者对场景已用到的接口结构相同，所以这一更新不改变执行；它的作用是让新加入的接口也有确定的基线；
- 适配提交（Release 方案 5.7）：取目标修订。

### 4.2 生效修订

一次执行使用的修订：

> 生效修订 = 已验证修订所在版本线中，**最新的**、且**场景用到的每个接口的 `shape_hash` 都与已验证修订相同**的修订。

等价表述（已定，D-5）：场景的**可用集合** = 该版本线内、场景用到的接口结构与已验证修订完全相同的全部修订；生效修订 = 可用集合中**最新**的一个。可用集合不一定是连续区间——结构「改了又改回」时，中间那些结构不同的修订不在集合内。

- 只改了评审状态、说明、词条，或新增了与本场景无关的接口的修订，自动生效。
- 场景用到的某个接口结构发生变化（包括只改 binding），生效修订停在变化之前，平台提示「定义已修正」，由线内修正适配处理（Release 方案 5.2）。
- 计算由 plate 提供（Release 方案 4.4），数据只需 manifest 的 `shape_hash` 与场景的接口列表。
- 解析只在一处发生：平台在入队时解析，并把解析结果作为执行副本的精确修订交给 `/convert`；`/convert` 本身不解析（Release 方案 4.5）。这样单场景与 Suite 使用同一套解析结果。

**不变量 I-1**：plate 发任何修订，都不会改变任何场景的执行；执行只取决于场景的声明，以及「结构完全相同」这一可验证的条件。

### 4.3 入库标准

一次执行计入入库标准，当且仅当：
- 没有任何系统声明为 `working`；
- 生效修订中，场景用到的每个接口都是已评审状态。

其他接口是否有草稿，与该场景无关。评审完成后发出的修订会被自动生效（4.2），入库标准随之满足，不需要用户操作。

### 4.4 执行记录与 Suite

- 执行记录落 `plate_pins`：每个系统的生效修订。
- Suite 要求同一系统在各成员中版本线一致，且整个 Suite 使用同一个修订。每个成员的**可用集合** = 其所在版本线内、该成员用到的接口结构与各自已验证修订完全相同的全部修订（不一定是连续区间，4.2）；入队时取所有成员可用集合的**交集**，用其中最新的修订。交集为空（某成员已验证的修订，晚于另一成员接口发生变化的修订，或结构抖动吃掉了公共修订）时拒绝执行，列出需要做线内修正的成员。

## 5. 环境与版本线

环境声明「每个系统部署的是哪条版本线」，用于：执行时比对场景的版本线并告警、适配时推荐「保存为副本」还是「直接保存」、判定版本线退役。

平台现在没有环境实体：服务别名（`service_aliases`）只有 `base_url`、`group_tag`、`credential_alias`，`group_tag` 只是字符串。承载方式已定（原第 11 节 V5，2026-10-10 按 B）：

| 做法 | 内容 | 评价 |
|---|---|---|
| A | 服务别名上加 `sut_line` | 不新增实体，但同组别名需各自设置，容易不一致 |
| B | `group_tag` 升级为环境组表，承载各系统部署的版本线 | 语义最清楚；属于新增实体，需单独评估必要性 |
| C | 只在集成任务上声明期望的版本线 | 最小改动；手动执行时没有依据 |

**已定（2026-10-10，Codfish）：按 B 实现**——环境组表 `environments` 与 `service_aliases.group_tag` → `environment_id` 外键，字段与迁移见 Release 方案 v4.1 第 11 节。环境是本模型中真实存在的概念，分散成字段是妥协。

## 6. working 的定位

working 是 main 当前树的定义，只用于 plate 编写者在编排页查看刚合入定义的效果。场景可以声明 `working`（预览），但：
- 不计入入库标准，集成任务拒绝触发；
- 没有固定基线，适配时一律按「目标修订试算」处理（Release 方案 5.6）；
- 测试阶段应声明新版本线的修订，而不是 working；
- 预览执行记录 working 快照的来源 commit，以便追溯；
- 维护分支上的编写者没有在线的 working 预览（plate 服务加载的是 main），用 `plate check` 与本地启动的 plate 服务自查。

## 7. 查询

plate 数据查询的 `ref` 写法：

| 写法 | 含义 | 使用方 |
|---|---|---|
| `<line>#<n>` | 指定修订 | 平台编排、执行、适配（必须用此写法） |
| `<line>` | 该版本线的最新修订 | 浏览页、CLI、Agent |
| `working` | main 当前树 | 编写者 |
| 缺省 | `working` | 编写者工具的默认视角 |

平台的编排、执行、适配调用都必须带 `<line>#<n>`，缺省时报错（`REF_REQUIRED`），由接口约束保证，而不是靠约定。平台的浏览页可以使用 `<line>`。

## 8. 发版流程约定

| 被测系统阶段 | plate 动作 |
|---|---|
| 新版本开始开发 | 从 main 拉出当前版本线的维护分支；main 修改 `line` 与 `predecessor_line` |
| 提测 | 新版本线发第一个修订；测试人员把场景适配到这条线 |
| 测试中 | 定义修正与评审持续合入，按需发修订；结构有变化的接口在 manifest 的 `corrections` 中标出 |
| 上线前 | 评审收尾，发修订；场景的入库标准自动满足 |
| 上线后旧版本仍在生产 | 旧版本线在维护分支上继续发修订 |
| 旧版本下线 | 环境不再声明旧版本线，旧版本线退役 |

## 9. 不变量

| # | 不变量 | 保证方式 |
|---|---|---|
| I-1 | plate 发修订不改变任何场景的执行 | 4.2 生效修订规则 |
| I-2 | 修订不可变 | 内容寻址；构件随签发入库；装载时校验 hash |
