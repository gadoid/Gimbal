## 一、调研发现（改变了原方案假设的部分）

四份代码调研（地址链与别名、凭证与令牌范围、carry 分层与漂移、项目区影响面）里，下面这些与方案的隐含前提不一致，直接影响切片和工作量。

| # | 发现 | 影响 |
|---|---|---|
| F1 | **运行时根本没有「选环境」**。`RunScheme` / `RunRequest` 都没有环境字段（旧 `RunRequest.env` 已随 D2 退役）；`environments` 表只有 `lines`（系统→版本线），**没有任何地址**；环境只通过 `service_aliases.environment_id` 间接影响 adhoc 版本选择和混环境告警 | 方案 4.2 的「环境：本次显式 > 方案 > 项目默认 > 个人偏好」是**全新链路**，不是迁移。P2 不只是建部署表，还要给方案 / 执行请求 / 项目 / 个人偏好加环境字段，并在派发、预检、指纹、导出各处带上环境 |
| F2 | **环境没有前端写面**（`api/environments.ts` 只有 list，注释「写面后端在，前端暂无入口」） | 部署表要有维护页面（Admin），P2/P7 要补 |
| F3 | **个人别名与共享别名在运行时完全相同**：`base_urls_for` / `credential_aliases_for` 只按 `alias_name`（主键）查，没有个人优先级；差别只在写权限（users.manage）和删用户时的处置 | P6 去 `owner_user_id` 的迁移比预想简单：名字本来就全局唯一，只需把这些别名名下的 carry 行转为属主的个人层 |
| F4 | **carry 是两张全局表**（`carry_service_bindings` 按服务名/别名名为键，`carry_global_defaults`），无作用域、无属主；现行三层链 = 精确别名键 > 基础服务键 > 全局默认 | P4 的「作用域」与现行「键层级」是两个正交维度，合并顺序要先定（见待定 D3） |
| F5 | **预检完全不算 carry；同意指纹不含 carry 值**；编排页的 carry 提示（`utils/carry-hint.ts`）只看基础服务键，**与运行时不一致**（别名键覆盖被忽略，存量缺陷） | P5 统一解析入口的收益比预想大，也说明「四处输出全等」测试必须从零建；carry 提示的不一致可先作为 P5 的首个修复项 |
| F6 | **执行器的 `users` 条目是 `extra='forbid'`**（`url/username/password/token_type/expires_in/refresh_token` 六字段） | 账号级字段（orgNo / opId）**不能**塞进凭证条目，只能经 `${slot.X.field}` 在派发前解析成 carry / 模板字面值——与方案「执行器不改」一致，但要写成硬约束 |
| F7 | **令牌范围的凭证集是 `access_token_scopes.auth_id → auth_sessions.id`（CASCADE）** | P3 改键时必须把范围行重映射到槽位绑定 id，否则 CASCADE 会静默清空全部令牌的凭证范围 |
| F8 | **suite 成员靠两条组合外键钉死「同属主」**（`(suite_id, owner_id)` 与 `(scenario_id, owner_id)`，DEFERRABLE） | 项目 suite 的成员由不同成员创建，**同属主外键必须改为同区约束**；这是 P1 的结构性改动，不是加一条 422 |
| F9 | 属主等值比较在 routers/services 约 **132 处**（suites 21、users 19、integration 16、shares 12、me 11 …）；但列表侧可见性已收敛到单个 SQL 谓词源 `scenario_query.visibility_clause` + `ref_exists_clauses`，表 B 也是单入口 `can()` | 项目谓词能集中落在表 B 与 `visibility_clause` 两处；132 处里大部分是写面属主判定（项目区写权按成员角色），需要逐处归类，工作量集中在 P1 |
| F10 | 执行可见性只认发起人（`can_view_execution`），suite 运行列表只列发起人自己的执行 | 方案 9.3「项目区执行对成员可见」要在 `can_view_execution` 与执行列表基础条件加项目分支 |
| F11 | 「析出」流程（`scenario_import._service_plan` + `analyze_services`）已能按解析链算出一致 / 不一致 / 敏感路径与冲突报告 | P8 提升流程可直接复用：给 `_local_value` 加项目层即可产出冲突清单 |
| F12 | **适配批次的权限口径不一**：开批次 / 看详情 = users.manage（Super Admin），列表 = ops.write；方案 2.1 把「适配批次」列为 Admin 职责。批次内写操作此前仅需登录（11-07 收尾已补门为 users.manage） | 是否下放到 Admin+、以及批次能否改写他人**私有**场景（方案 1.3 把适配批次列入要收窄的 admin 分支），需要定（待定 D5） |

## 三、各切片要点（待定项定下后展开为 W 段格式）

### S1 项目区骨架
- **表 B**：新谓词 `project`（主体是对象所属项目的成员；写面再按 `project_members.role` 区分 admin / member）。`can()` 在 `ref` 之外加 `_pred_project`；`tests/authz_expected.yaml` 同步扩项目轴。
- **SQL 可见性**：`visibility_clause` 加「`project_id IN (我所在项目)`」一支，列表 / facets / 执行 q 搜索 / 适配陈旧列表自动跟随（F9）。
- **执行**：`can_view_execution` 加「执行所属场景在我所在项目」分支；执行行是否要冗余 `project_id`（列表性能）在展开时定。
- **suite 同区**：两条同属主组合外键换成「成员与 suite 同 `project_id`（都为空时同属主）」，DB 侧用触发器或应用层 + 迁移校验（F8，展开时定）。
- **写面归类**：132 处属主比较逐处归类为「私有区属主判定（不变）/ 项目区按角色 / 删用户处置」三类，产出清单后再改。
- **测试**：matrix_b 扩项目轴（成员 / 项目管理员 / 非成员 × 私有 / 项目 / 公共）；跨区成员 422；执行可见三方；删用户处置。

### S2 环境选择链 + 部署表
- **链路**：本次执行显式 > 方案 > 项目默认 > 个人偏好；都没有时的兜底见待定 D2。
- **迁移一致性**：迁移前后逐别名比对地址解析结果（实施文档风险表）；`service_aliases.environment_id` 为空的别名如何落部署表要先统计存量。
- **指纹**：第七要素从「别名 base_url 集」改为「部署表 [系统][环境] 集」——口径变化即全员暂停，按方案 §1.2 预期机制公告。

### S3 槽位绑定
- **键**：`(owner, system, env, slot)`；一个槽位多个绑定、每槽一个默认。
- **迁移**：每条存量会话 → 同名槽位的默认绑定；`system` 从引用该凭证的别名的基础服务推断，推断不出的落「未归类」由用户认领（展开时定）。
- **范围重映射**：`access_token_scopes.auth_id` 先指向新绑定 id 再删旧列，避免 CASCADE 清空（F7）。
- **约束**：账号级字段只经 `${slot.X.field}` 进 carry / 模板（F6）。

### S4 carry 分层
- **合并顺序**（待定 D3 的推荐）：作用域为外层（全局 < 项目 / 个人），每个作用域内部沿用现行键层级（别名键 > 基础服务键 > 该作用域默认）。
- **读接口**：`GET /carry/bindings` 只返回全局 + 我所在项目 + 我自己的个人层（10.5）。

### S5 唯一解析入口
- **输出**：每个值带来源（作用域 + 键层级 / 部署表 / 槽位绑定），供生效预览直接展示。
- **影子比对**：先在执行路径并算新旧两套、只记差异日志；差异为零后再切换四个调用方。
- **全等测试**：同一组输入跑执行 / 预检 / 指纹 / 预览四个调用方，输出全等。

### S6 别名瘦身 + serviceBindings 收窄
- **存量清洗**：方案 payload 里的 `url` / `authAlias` 迁移时剥离并出报告（哪些方案丢了什么），通知方案属主。
- **参照**：adhoc 的整体拒收（`services/adhoc_run.py`）。

### S7 页面与流程
- **提升**：复用析出（F11），冲突清单由项目管理员裁决；槽位绑定不随之移动。
- **share_ref 退役**：引用者加入项目或转私有副本；迁移脚本先出清单给属主确认。
