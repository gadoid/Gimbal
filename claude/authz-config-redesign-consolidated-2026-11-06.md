## 〇、总原则

1. **凭证跟着人走。** 每一次出站请求都使用某个注册用户自己的凭证，每一次入站调用都使用这个用户的令牌。系统里没有共享凭证，也没有不归属于具体人的执行身份。
2. **公共内容只读。** 公共用例不能直接执行，没有例外。
3. **地址随环境变化，不随人变化。** 环境和地址是全局事实。项目可以选择用哪个环境，但不能定义环境。
4. **槽位是凭证和 carry 唯一的交汇点。** 两者互不直接绑定，执行前为每个槽位选一个账号绑定。
5. **不新增模块。** 所有改动都落在现有表、现有服务、现有页面上。新增的表在第六节单独列出。

## 一、平台分区

### 1.1 三个区

| | 私有区 | 项目区（M2） | 公共区 |
|---|---|---|---|
| 内容 | 个人用例、草稿 | 团队资产 | 只读模板、示例 |
| 谁能看 | 只有本人；任何平台角色都看不到 | 项目成员 | 全员 |
| 谁能改 | 本人 | 按项目角色（第二节） | 维护者；Admin+ 可以下架 |
| 能否执行 | 本人执行 | 项目成员执行 | **不能执行**，见 1.2 |
| 用谁的凭证 | 执行人自己的 | 执行人自己的 | — |
| 使用哪层 carry | 全局 < 个人层 | 全局 < 项目层 | — |

### 1.2 公共用例的两条使用路径

1. **复制到私有区**：也就是现有的不变量 7。复制即钉住版本，之后的修改与原件无关。
2. **订阅到集成**：用自己的凭证订阅，逐项确认字段配置。复用现有的订阅实例和知情同意指纹（`integration_runner.py:471/1016`）。公共用例被修改后指纹不再一致，实例会暂停，等订阅人重新确认。

公共内容被链路引用（setup / teardown）时，也只能复制进来，不能活引用。

### 1.3 私有区的边界

- 「私有区对任何平台角色都不可见」意味着要收窄现有代码里所有对他人私有对象的 admin 分支，不止 v5 列出的 4 处。完整清单见评估文档第一节第 2 条：`_ownership.py` 的五个判定，越过属主的删除和发布，分享、个人集成模板、数据集、报告定义、适配批次。
- 删除用户时，**保留现有的「删除 / 保留 / 转让」三选一**，不实行 v5 的「一并清理」。
- 管理员重置密码不能成为绕过私有区的通道，见 10.1。

## 二、角色分级

### 2.1 平台角色（M1）

| 新角色 | 来源 | 职责 |
|---|---|---|
| Super Admin | 原 admin | 用户管理（注册、停用、删除及处置、角色变更、重置密码）；同时拥有 Admin 的全部能力 |
| Admin | 原 member | 维护服务别名注册表、部署表和环境、全局 carry、平台模板；审计；适配批次 |
| User | 原 user | 管理自己的内容；签发个人令牌；导入；订阅 |

和 v5 相比的变化：

- 平台凭证池取消（第三节），Super Admin 不再承担「凭证保管」的职责。
- 表 A 删除「平台任务 / 平台令牌 / 平台身份」这一行。不存在平台主体，也就不需要「平台主体」列。
- `__platform__` 不再参与任何执行，只作为平台模板的持有者。

### 2.2 项目角色（M2）

| 阶段 | 角色 | 能力 |
|---|---|---|
| M2a | 项目管理员 | 管理成员；编辑项目层 carry 和环境默认值；收录提升上来的用例；管理所有项目内容 |
| M2a | 项目成员 | 读写和执行项目内容 |
| M2b | 项目用户 | 只能读和执行，和项目令牌一起上线 |

对约 10 人的团队，首期只做两级就够了。

### 2.3 判定机制（M1 落地）

- 表 A（能力 × 角色）和表 B（对象 × 动作）是唯一的规则来源，代码只负责查表。
- `/auth/me` 返回按表 A 求出的能力列表，前端改为判断能力，不再判断角色。前端实测（HEAD `85f8e2d`）：`'admin'` 81 处 / 28 文件、`isAdmin` / `is_admin` 96 处 / 40 文件、`'member'` 48 处 / 20 文件——其中 `UsersAdmin.vue` 与 `api/*` 里的 `'member'` 是角色枚举本身（类型定义、zod 校验、单选值），随 W1 更名自然消失，其余改成判断能力后只需要迁移这一次。
- 后端行内角色比较实测约 70 处（routers ≈60、services ≈7，集中在 access_tokens / suites / integration / users / shares / _ownership），统一改为查表；SQL 侧按角色选人群的写法（`User.role.in_(("admin","member"))`——`access_token.py:573` 与告警扇出三处）改写为 `User.role.in_(roles_with(cap))`，否则 M1 到 C1 的窗口期告警会漏发 Super Admin（评审 R5）。grep 守卫同时扫描 `routers/` 和 `services/`，正则覆盖属性比较 `.role ==`、SQL 集合 `.role.in_(`、列比较 `User.role ==` 三种形状，`_ownership.py` 豁免；守卫必须与 W1 更名同版本生效，否则枚举字面量会误报。
- 测试由表驱动生成，另维护人工审定快照（`tests/authz_expected.yaml`，约 20 条关键期望，表变更必须同步改——见实施 W2；评审 E5）。

## 三、平台任务变更

### 3.1 平台模式退役

| 项 | 改造后 |
|---|---|
| 平台模式的执行身份 | 取消。平台任务只作为**平台模板**存在，要使用就以个人身份订阅，用自己的凭证执行 |
| 平台模板 | 一种公共模板，由 `__platform__` 持有、Admin+ 维护，不会因为某个人离开而失去维护者 |
| 平台凭证池 | 取消 |
| D9（平台模式可以执行公共场景） | 取消。「公共不能执行」不再有例外 |
| 平台令牌（不带 grant 的入站调用） | 取消。入站一律使用个人令牌（M1），或项目令牌（M2b） |
| 平台执行的可见规则、对 member+ 的告警扇出、平台模式不能临时调用 | 一并取消 |

接受的代价：没人订阅的模板不会执行；N 个人订阅同一个模板，被测系统就收到 N 次请求。

### 3.2 外部调用方

- **M1**：只做查询的 Agent，使用白名单用户（专用注册账号，绑定只读凭证）的个人令牌。**每个 Agent 各发一枚令牌**，审计里按令牌名区分。「只读」由这个账号在被测系统里的权限保证。
- **M2b：项目令牌**
  - 令牌表的 `kind` 从 `platform` 改为 `project`，加上 `project_id` 和负责人字段。
  - 负责人是一个**指定的**项目管理员，不是「项目管理员」这个角色；执行时使用负责人的凭证。
  - 只能访问本项目区，访问不到负责人的私有区。
  - 换绑：令牌密钥不变；换绑后令牌先暂停，等新负责人确认后恢复。确认复用订阅的知情同意机制。

### 3.3 自举系统 `platform`

用执行人自己的 Gimbal 个人令牌，以 bearer 方式施加。`platform` 的认证过程需要补一种「静态令牌」认证方式：直接施加，不走登录。

### 3.4 被取代的旧口径

- 2026-10-30：入站身份挂在外部系统别名上；写操作要额外带头字段标明用户身份。改为个人令牌直接表达。
- 2026-11-01：平台模式只能执行公共场景或同属主场景；平台执行只有别名属主和 admin 可见。
- 2026-11-02：平台模式不能使用临时调用。
- v4 中平台令牌的全部规则。
- 不一致清单中的 #6、#7、#9，以及前端修复 r2 的遗留项 1、2，随之消失。

## 四、凭证与 carry 解耦

### 4.1 三类对象

**配置项（服务别名），不属于任何个人**

```
fin-maker
  系统: fin    环境: sit             → 地址查部署表 [fin][sit]
  槽位: maker                        → 声明要用哪种身份
  carry:
    currency   = CNY                 ← 普通值
    orgNo      = ${slot.maker.orgNo}  ← 账号级字段，取自槽位
    operatorId = ${slot.maker.opId}
```

- 别名名字由 Admin 维护全局注册表。carry 分三层：全局默认、项目层、个人层。
- 哪些字段跟着账号走，属于配置项的定义。

**槽位绑定，只属于本人**

```
我的绑定
  maker-A：账号 A，orgNo=0101，opId=OP01   （默认）
  maker-B：账号 B，orgNo=0202，opId=OP07
```

- 一个槽位可以有多个绑定，每个槽位有一个默认绑定。
- 只有本人能看到和填写；不分发，不随用例提升而移动。

**方案：只做选择，不存值**

- 选择环境、选择每个服务键用哪个别名（`fin → fin-maker`）、选择数据集。
- **删除** `serviceBindings` 中的 `url` 和 `authAlias`：地址由部署表给出，凭证由槽位绑定给出。
- 方案的归属跟着场景走。方案里不存个人绑定。

### 4.2 执行时的解析链

1. **环境**：本次执行显式选择 > 方案 > 项目默认（项目区）> 个人偏好（私有区）
2. **地址**：部署表 `[系统][环境]`（与现有地址链的关系见 9.2）
3. **槽位绑定**：本次执行时的选择 > 本人的默认绑定。只能选自己的绑定
4. **carry**：
   - 项目区：全局 < 项目层
   - 私有区：全局 < 个人层
   - 账号级字段只从槽位绑定取值。数据集行可以覆盖业务字段；要换账号就换绑定，而不是覆盖单个字段
5. **预检**（失败就中止，不再「告警后继续」）：
   - 每个槽位都已绑定；
   - 同一次执行里，不同槽位不能落到同一个账号上，只对声明了唯一登录的系统检查；
   - 缺失时提示具体的「系统 / 环境 / 槽位」。

**唯一解析入口。** 执行、预检、订阅同意指纹、生效预览这四处，统一调用同一个有效配置解析函数。函数放进现有的 `run_prepare` 或 `carry_injection` 里，不新建模块。同意指纹要包含选中的槽位绑定。`${slot.…}` 由平台在派发前解析成字面值，执行器只看到最终的值，执行器的 schema 和 CLI 不受影响。

**并发。** 不做全局的同凭证串行。真有唯一登录的系统，就在它的认证过程里声明 `session_policy: exclusive`，只对它让同一绑定串行执行。

### 4.3 页面

- **配置项页**（由 `/service-admin/:alias` 扩展而来）：
  - 基本信息：系统、环境、地址、槽位声明；
  - carry 按层分页签：全局（Admin+）/ 项目（项目管理员）/ 我的（本人）；
  - **生效预览**：选一个区，显示合并后的取值，并注明每个值来自哪一层；
  - 槽位状态：显示「你已绑定 / 未绑定」，并跳转到个人设置。
- `/carry-config` 并入配置项页后退役。
- 槽位绑定放在个人设置里。变更适配继续作为独立页面。

### 4.4 流程

- **用例从私有区提升到项目区**：把用到的个人层 carry 复制到项目层，冲突时提示，由项目管理员决定。复用导入的「析出」流程。槽位绑定不随之移动。
- **新成员加入项目**：不分发任何东西。项目页根据项目用例用到的「系统 / 环境 / 槽位」推算出一份清单，提示成员还要绑定哪些。
- **数据集按账号驱动**（以后再做）：数据集行增加一列槽位绑定选择。

## 五、导入的口径（M1）

导入当前是 member+ 专属（`routers/scenario_import.py` 挂 `MemberUser` 门），会新建别名、写入 carry（`scenario_import.py:614/624`）。v5 计划把导入开放给 User，等于从侧门开放了别名的写权限。M1 期间：

- User 导入时，只允许「映射到已有别名」；
- `decision=create`（新建别名）需要 Admin+。

M2 引入槽位绑定和配置层之后，再评估是否放宽。场景里内置的凭证在导入时怎么处理，见 9.1。

### 9.1 场景内置凭证：直接破坏「凭证跟人走」 ⚠

## 十、遗漏核对后的补充（第二轮）

### 10.1 管理员重置密码 = 能接管任何账号 ⚠

- 现状：`POST /users/{id}/reset-password`（`users.py:344-392`）生成一个随机密码，**把明文返回给操作的管理员**（`:388-392`）。它**不会**让目标用户的个人令牌失效，也**不会**让 `token_version` 加一；`must_change_password` 全后端不存在。用户自己改密时这两件事都会做（`auth.py:146-217`，`invalidate_tokens` / `logoutOthers`）。
- 问题：
  1. Super Admin 重置之后，可以用新密码登录成那个用户：既能看到他的私有区，又能用他的槽位绑定去请求被测系统。这样「私有区不可见」和「凭证跟人走的审计」同时失效，等于一个没有登记的破窗通道。
  2. 管理员重置后，用户原有的令牌和会话仍然有效，和 11-04 定下的「改密时令牌置为过期」不一致。
- 处理（M1）：
  - 重置后的临时密码只能用于**首次登录改密**：用临时密码登录后，除 `/auth/me`（响应带 `must_change_password`）、`/auth/refresh`、改密接口外一律 403 `password_change_required`——前端登录态靠 `/auth/me`（`stores/auth.ts:8`），me 不能拦。临时密码仍返回给管理员一次（当前没有其他交付通道；本节已接受「能接管、做不到悄悄接管」）。
  - 重置时让目标用户的个人令牌失效（复用 `REASON_PASSWORD`），`token_version` 加一。
  - 通知目标用户，并在审计中记录（审计这一项现在已经有）。
  - 这样管理员仍然可以接管账号，但做不到悄悄接管：用户原来的密码会失效，会收到通知，后续操作都留在审计里。

## 十二、实施后评审修订（2026-11-07）

M1–C3 落地后的一轮评审，六项，均已在 `feat/authz-m1` 实现：

1. **集成通知只发持有人**。平台模式退役后每个实例都有持有人，但「连续失败」仍走平台时期的兜底分支，把任务名和错误信息群发给全体 Admin+——违反私有区不可见，功能上订阅人自己也收不到。改为连续失败 / 自动暂停 / 同意闸暂停 / 结论通知一律只发持有人；兜底分支、`access_token.fanout_members` 与表 A 的 `platform.alerts` 能力一并删除（表 A 现为 `users.manage` / `ops.write` / `alias.write` 三项）。
2. **同属主拷贝不剥离**。`copy_scenario` 只在新属主 ≠ 原属主时剥离 `config.users` 与数据集敏感列；作者给自己「另存为」、给自己做变更适配副本保留原样。
3. **发布不改原件（取代 9.1「公开时剥离」与 10.6）**。此前发布会清空作者原件的内置凭证并删除数据集敏感列——作者自己再跑缺凭证和密码列，下架后也恢复不了。改为原件永不修改，凡交到**非属主**手里的形态各自脱敏：
   - 读：场景详情 / draft / 发布与下架回包去 `config.users`；数据集详情与列表预览（含引用闭包读者）剥敏感列；
   - 拷贝：跨属主拷贝剥离（第 2 项）；
   - 执行：内置凭证主规则（执行人 ≠ 属主当空）不变；另在 `run_dispatcher.dispatch_target`、`graph_dispatch.resolve_graph_units`、`integration_runner.run_instance` 三个执行入口对非属主剥数据集敏感列；执行快照与任务参数去 `config.users`（顺带修掉引用执行快照外带作者明文的存量漏洞）。
   - 订阅同意指纹仍按原行计算（同一模板全体订阅者一份指纹，不因持有人不同漂移）；E1 的「重新发布触发剥离 → 指纹变化」连带随之消失。
4. **内置凭证预检告警上页面**。`builtinAuthShadowed` 此前只在接口返回：执行器预检行补告警并指向「我的凭证」；suite 预检（`/suites/{id}/validate`）同算（聚合逐主体成员、编排逐单元），条目 `builtin_auth_shadowed`。
