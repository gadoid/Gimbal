## 0. 处置原则

1. **不物理删除**(适用范围:方案/设计/计划类文档;评审记录类按原则 6 另行处置):分享设计文档曾有误删事故;历史结论的价值在「可追溯」,git 历史保留 ≠ 仓库内可以语义混乱。
2. **原位注记为主,物理搬动为例外**:文档间交叉引用密集(内链 + 记忆/评审引用路径),搬动破链;仅对 grep 证实零引用的孤儿才移归档目录。
3. **状态行强制**:方案文档头部必带状态行,生命周期四态:`草案 → 定稿 → 已交付(带 commit/批次指针)→ 被取代(指向继任者,注明哪些章节仍有效)`。**plans 区豁免指针要求**:`platform plans/` 批量注记写「已交付(见 git 历史)」即为合规,逐份精修指针仅适用于 `claude/` 设计文档。
4. **归档有先例**:`design/archive/`(8 份早期设计)、ADR `0003-retired-features-log.md`(退役日志)—— 沿用,不新建机制。
5. **不凭记忆断言状态**:W1 逐份对照 git 与代码现状核实(见 §2 各「待核实」项)。
6. **评审记录不沉淀**(2026-10-16 拍板):评审轮处理完毕后,评审记录文件**不入仓、即删** —— 采纳项与论证折叠进设计文档的修订记录(如归一方案 §9),仓库只保留调整后的设计文档与配套清理/实现文档。适用于本项目今后所有评审轮;**存量纯评审记录类文档(plate-s1-review、架构评审 2026-10-09、m2 feasibility)owner 已拍板删除方向(2026-10-16),W1 执行前必须 grep 全仓引用**(比照原则 2;已知首例:`plate-design.md:59` 引用 `claude/plate-s1-review.md` —— 处置 = 改引处指向 git 历史或一并删引段,再删文件)。
7. **活文档例外条款**:「活文档区不动」不覆盖**描述被退役对象的活文档** —— 此类文档随退役批同提交更新(首例:`docs/概念地图.md:17` 的外部锚点描述,与归一方案批3 同提交)。
